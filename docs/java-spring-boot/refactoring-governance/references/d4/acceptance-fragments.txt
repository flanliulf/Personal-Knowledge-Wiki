0006
0007	保留原 AC-01—AC-32、111 个 `CASE-D2-*`、16 个 `CASE-D3-*`、146 个 `OC-*` 和24个 `CASE-PB-*` 稳定ID。新增6个 `CASE-D4-R01`—`R06`，对应本轮 `D3R-01/02`；操作库另新增 `OC-21-BP/BN`、`OC-23-FP/FN` 四个技术case及其明确variant。合计 **307 个设计标识**：133个治理/修订正文、150个操作用例、24个专项用例。旧D2/D3前缀仅为稳定标识，当前规范版本均为D4。标识数量不是执行次数或实际覆盖率。
0008
0009	每例固定逻辑受评对象 `verdict_subject={kind,ref,scope}`、前提、动作和预期状态。实际执行前只补真实版本/hash、fixture、配置和命令，不临时换对象。fixture 与独立 oracle 先由验收方固定，不能把被测 Skill 的自述作为结论。表中 `PASS/FAIL/NOT_CHECKED` 是将来的预期对象结论；本轮执行状态一律 `NOT_RUN`。
0010
0011	基线、候选实施资格、候选行为、改后代码、计划和测量分别判断。已观察的基线失败不能自动归因为候选行为回归。针对候选的直接违反证据可以是受控运行观察，也可以是前提充分的独立语义证明；不必为证明明显错误而先执行危险候选。正确拒绝候选可形成计划 PASS，但不使候选或代码 PASS。执行故障也不自动等于代码 FAIL。允许结果引用多个 supporting verdict，保留各自对象，禁止跨对象混成一个结论。

0016
0017	| 集合 | 使用时点与输入 | 选择与完成条件 |
0018	|---|---|---|
0019	| `qualification_case_set` | 将来实现治理核心、canonical recipe、adapter 或 host 后验证其资格；输入实现版本、声明能力及适用分支 | 选择相关治理/OP/PB/宿主正反分支；关键拒绝分支不能因fixture未建而悄悄删掉。未适用有理由，缺绑定标NOT_RUN；各层分别通过才证明对应能力 |

0024	`OB-01`—`OB-18` 是义务族。[主文唯一实例契约](java-springboot-refactoring-governance-design-d4.md#d4-obligations)规定：去重还必须匹配不可变 `subject_identity={kind,ref,revision_or_hash}`；已唯一绑定身份与版本的immutable ID可间接引用，不重复存hash。`subject_stage`独立保留。仅同对象、同版本、同阶段、同有效规则集合/性质/scope/profile的多路由可以合并理由。血缘关系、路径相同和阶段相同均不能替代身份。不同对象或版本分别保留实例与结论。

0051	## 子手法资格选择（Recipe Qualification Selection）
0052
0053	[操作库资格卡](java-springboot-refactoring-governance-d4-operations.md#d4-qualification)是子手法 `declared_capability → supported_variant → required_branch → case/variant` 的唯一规则权威。机器规格的 `recipe_qualification_index` 是同源派生视图；`case_index` 反向关联 `canonical_recipe_refs`、`recipe_branch_refs` 及具体 `recipe_branch_bindings`。不按父OP的所有用例推定每个子手法都已覆盖。alias先解析canonical owner，再按入口语义和明确能力声明确定确切variant，取该variant同一必要分支；不允许从缺失或pending变体回退到同owner的其他已映射变体。相关链接不扩大声明。
0054
0055	Builder与Factory的技术性质及每个正反variant只在OP-21/OP-23维护。本册的R05/R06仅验证资格选择、缺口识别及负担边界。原 `OC-21-P/N` 继续保护参数对象；`OC-23-P/N` 继续保护CQS对应分支；`CASE-D3-R07` 继续验证owner解析。三者均不能代替Builder/Factory缺少的技术分支。
0056
0057	`mapped_in_design` 表示已固定必要分支及映射；`qualification_pending` 表示仍有明确映射缺口。两种状态均不等于技术实现通过。将来声明recipe资格时，还须绑定实现版本及全部适用分支，实际充分证据齐全才可PASS。其他具名子手法保留已映射范围和pending原因，未覆盖范围不承诺资格支持；普通工程任务仍按自己的 `required_check_set` 选择最低充分证明，不为每次任务跑全部资格反例。若检查目的只是完整报告缺口，治理记录可以完成；缺口不能从资格结论中消失。

0380	治理、adapter、host、文档、代码和测量分层报告。真实宿主入口发现不能用静态frontmatter代替；正确阻断的治理PASS不能写为未执行候选代码PASS；可比性能PASS不能覆盖行为FAIL。环境不可用、零测试、错模块、skip、过期证据和未满足独立审查均按对象及必需实例保留缺口。
