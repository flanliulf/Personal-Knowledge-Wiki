## 执行结论（Executive Findings）

这些 Skill 适合用来设计重构体系的内容骨架，尤其是经典手法、坏味道诊断、行为保持和小步验证。**不建议按安装量或仓库 star 直接整包采纳。**两项热度指标反映的对象不同，定义本身还存在复制、固定版本、硬阈值、宿主依赖和索引过期等问题。

## 建议采用的分类（Recommended Taxonomy）

下表是本次设计推导。详细事项和来源分别见 [完整清单](classification-checklist.md)。

| 分类 | 主要事项点 | 采纳判断 |
|---|---|---|
| C01 命名与意图表达 | rename、统一领域词汇、常量、有效注释 | 采纳；核查框架和外部名称契约 |
| C02 方法与表达式 | 提取/内联、变量、查询、分阶段、算法替换 | 采纳；不由行数自动决定改写 |
| C03 条件与控制流 | 守卫、条件分解/合并、循环拆分、控制标志 | 采纳；保留求值与副作用顺序 |
| C04 职责与特性归属 | 拆/并类、移动字段/方法、去重、代理层取舍 | 采纳；避免一方法一类与错误共享 |
| C05 数据与领域类型 | 封装、值对象、不可变性、派生状态、record | 采纳；先核对相等性和数据契约 |
| C06 调用与 API 契约 | 参数、标志参数、查询/修改分离、可见性 | 采纳；跨公开边界提高风险等级 |
| C07 继承、组合与模式 | 接口、层级调整、委托、模式选用与撤销 | 条件采纳；以现实变化压力决定 |
| C08 模块、依赖与迁移 | package/模块、循环依赖、DI、渐进迁移 | 采纳；显式消费者和兼容策略 |
| C09 Java 现代化 | Lambda/Stream、时间、集合、var、switch 等 | 条件采纳；按实际 JDK 与 preview 状态 |
| C10 Spring 与持久化 | 注入、配置、事务、AOP、JPA、查询边界 | 专项采纳；不用固定框架覆盖所有项目 |
| C11 并发、资源与异常 | 状态所有权、锁、取消、资源释放、错误传播 | 高风险专项；需要运行层证据 |
| C12 性能与测量 | profiling、分配/CPU/I/O、查询/缓存、前后对照 | 条件采纳；无热点与基线不开展优化 |

G 横切流程涵盖：范围确认 → 只读诊断 → 行为契约 → 安全网 → 最小步骤 → 预览/试点 → 验证 → 结果与剩余风险。测试、授权与回退是所有分类的共同要求，不宜作为与“提取方法”并列的互斥分类。

## 应保留、修订与补充什么（Adopt, Revise and Extend）

### 可以保留的内容（Adopt）

1. 经典手法及其反向手法。提取与内联、隐藏代理与移除中间层都应存在，避免体系只有“继续抽象”这一种方向。
2. 坏味道先于手法。每条发现包含具体源码、维护后果与预期收益，而非只贴 SOLID 标签。
3. 行为保持、小步、可逆和有证据的验证。
4. 遗留代码的特征测试与接缝策略。
5. 批量转换的预览、试点与消费者核查。
6. 性能工作的测量先行和按证据保留/回退。

这些内容分别在 [经典目录](https://www.skills.sh/smallnest/goal-workflow/refactor)、[四模式路由](https://www.skills.sh/akillness/jeo-skills/code-refactoring)、[遗留代码](https://www.skills.sh/wondelai/skills/working-with-legacy-code)、[高性能](https://www.skills.sh/jabrena/plinth/145-java-refactoring-high-performance) 的定义中可找到依据。

### 需要改写的规则（Revise）

| 来源中的做法 | 问题 | 建议修订 |
|---|---|---|
| LOC > 15、至少提取一个方法 | 将诊断信号变成必须改写 | 阈值只触发检查，以实际职责与维护成本决定 |
| 固定输出 Java 17 或默认 Java 21+ | 可能与目标 toolchain 不符 | 从实际编译配置和源码确认版本，建立特性适用矩阵 |
| 全面 Stream/Optional/record 化 | 可能改变顺序、缺失值、可变性和数据契约 | 每项转换写清前提与反例；允许保留旧形态 |
| 默认 Maven 命令 | 不能覆盖 Gradle、特殊 wrapper 和多模块验证 | 由项目构建 profile 给出命令 |
| 强制 SOLID 或模式套用 | 可能增加类型和间接层 | 同时说明变化压力、替代方案和撤销条件 |
| 只匹配 failed=0 | 测试框架输出格式不同，可能误判 | 检查退出码与真实测试报告，并区分无测试、跳过和失败 |
| 更新 snapshot 再宣称等价 | 新结果可能覆盖旧行为的证据 | 先比较差异，预期行为变化另行授权 |
| 超过 10 个文件就文本批替换 | 不理解 Java 绑定、重载或反射 | 使用类型/符号信息，预览并试点 |
| 一律立即删除兼容层 | 不符合存在外部消费者的发布过程 | 显式选择内部原子迁移、并行兼容或分阶段废弃 |
| 固定宿主 Agent、MCP、知识目录 | 降低可移植性 | 作为可选 adapter，定义无工具时的降级与未验证结果 |

这些是对定义规则的适用性分析，不是运行后发现的产品缺陷。代表证据：[Extract Method](https://www.skills.sh/github/awesome-copilot/java-refactoring-extract-method)、[复杂度 Skill](https://www.skills.sh/github/awesome-copilot/refactor-method-complexity-reduce)、[批量重构](https://www.skills.sh/mhattingpete/claude-skills-marketplace/code-refactor)、[行为验证模板](https://www.skills.sh/aiskillstore/marketplace/code-refactoring)、[Clean Refactoring](https://www.skills.sh/dzhng/skills/refactor-clean)。

### 建议新增的能力（Extend）

下面是本次设计建议，不宣称 61 项来源已经完整提供：

- **消费者与边界契约**：源调用之外，补查反射、配置、SPI、序列化、SQL/XML、RPC 和二进制消费者。
- **框架运行语义**：Spring 代理、self-invocation、事务、缓存、安全、监听器、JPA lazy loading 与实体身份。
- **异常与资源时序**：关闭顺序、异常 cause、取消、中断、timeout 与锁顺序。
- **风险分层**：局部 private 方法、跨模块接口、数据边界、框架注解、并发与性能采用不同验证深度。
- **可证伪的验收**：明确什么结果会推翻“行为保持”“降低复杂度”或“性能提升”的判断。
- **来源治理**：源 revision、分类依据、支持文件完整性、许可和安装/加载验证分别记录。

Spring 的默认 proxy 模式具有 self-invocation 约束，说明“编译和单测通过”不足以覆盖所有方法移动风险。[Spring 官方说明](https://docs.spring.io/spring-framework/reference/data-access/transaction/declarative/annotations.html)

批量 Java 转换可评估 IntelliJ/LSP 或 OpenRewrite 等具备符号/类型信息的路径。OpenRewrite 的 type attribution 用于区分语法相似而语义不同的调用，Maven 插件提供 dryRun；本轮没有运行这些工具或替目标项目选择版本。[类型信息说明](https://docs.openrewrite.org/reference/type-attribution)、[dryRun 说明](https://docs.openrewrite.org/reference/rewrite-maven-plugin)

## 建议的体系结构（Proposed System Structure）

| 层次 | 内容 | 设计理由 |
|---|---|---|
| 入口与总协议 | analyze / plan / apply / verify；范围、证据与退出条件 | 让用户意图与允许动作清楚对应 |
| 诊断与手法目录 | 12 类事项，按需加载具体手法及反向手法 | 避免一次加载全部规则，也避免只有口号 |
| 项目 profile | JDK/release/preview、Maven/Gradle、模块、Spring/JPA/reactive | 技术前提可独立演进 |
| 专项安全规则 | 公开 API、数据契约、并发、持久化、性能 | 高风险行为有明确验证要求 |
| 可选工具 adapter | IDE/LSP、图谱、重复检测、结构化转换 | 工具缺失不伪造能力，工具成功不替代验收 |
| 证据与来源登记 | 验证结果、未验证项、源 revision、迁移后续 | 支持复核与更新 |

每个手法至少有 `operation_id`、问题证据、适用范围、前置条件、行为契约、步骤、验证、回退、停止条件和来源 revision。建议先完成这些字段，再决定拆为多少个 Skill；分类数量不应直接等于 Skill 数量。
