# 业务事件分析（Event Storming）

## 目标与边界（Purpose and Scope）

从业务结果出发，形成可追溯的行为需求分析。领域事件是业务人员关注的已发生结果；命令是促成结果的业务操作；执行者是角色或系统。输出事件—命令矩阵、独立查询、功能覆盖矩阵、候选概念、规则、统一术语和未决问题。

本包分析当前范围，不认定需求已批准，也不授权实现。事件分析不要求采用消息队列。发现的名词只是建模素材，不能直接认定为实体或聚合。业务已清楚且仅做技术架构改造时，不强行组织事件风暴。

## 输入与资源（Inputs and Resources）

输入包括业务范围、分析问题、可读取材料、资料版本和既有需求产物。用户已给出的信息直接复用。缺少核心材料时列出缺口；关键事实未知或冲突时，停止依赖该事实的结论并提出具体问题。

所有相对路径从实际包根解析，不依赖 CWD。每次分析先读取 [证据与交接契约](references/evidence-contract.md) 和 [详细流程](references/workflow.md)。交付前读取 [报告模板](assets/report-template.md)，按其字段组织结果；没有数据时注明 unknown 或不适用依据，不用空表掩盖缺口。

核对方法出处、版本或维护源包时读取 [来源记录](references/source-provenance.md)；设计或执行行为验证时读取 [行为用例](references/behavior-cases.md)；检查版本变化时读取 [版本记录](CHANGELOG.md)。这些资料用于方法追溯和维护，不作为目标业务事实。原课程及图片不是运行依赖。本包没有脚本、MCP 或其他 Skill 的必需依赖。

## 执行流程（Workflow）

1. 建立 scope、baseline 和 sources。明确当前行为、已批准目标及候选方案。确认分析是否适用；已有成熟用例或用户故事时，以现有结构补齐业务结果、规则和术语。
2. 按业务过程识别已发生结果。先保留参与者或资料的不同理解，再依据证据收敛。没有领域专家参与时，只能提出候选和问题，不能模拟专家确认。
3. 使用业务术语命名事件。区分主路径、可选路径和异常；只记粗略业务顺序。严格前置条件单独保存，不能从排布推断。
4. 为事件分析命令、执行角色和执行前所需查询。支持多个角色、多个读取对象；区分“已确认不需读取”和“尚不知道”。排除缓存命中等技术事件。
5. 从事件、命令、角色和查询提取候选名词。复用稳定 concept_id，同一事件涉及多个名词时保持 event_id 不变。保留合并、拆分、角色含义等问题。
6. 单独识别纯查询，并与既有功能清单逐项对照。核对修改、删除、退出、撤销及例外是否在范围内。未在事件视图展示的需求仍要登记；没有功能基线时明确覆盖结论受限。
7. 汇总规则、术语、证据和问题，按模板交付。检查每个结论的 evidence_ids 与 confirmation_status。最多两轮定点调整；需要新业务事实时按契约交付 needs_clarification。

## 交付与使用限制（Delivery and Limits）

统一输出 scope、baseline、sources、concepts、rules、decisions、open_questions 和 result_status，再附本包专用表。遵循契约的 confirmed、candidate、unknown、conflicted、rejected 状态，不能用 Agent 一致意见确认业务事实。

默认在对话中交付。用户明确要求保存时才写入指定位置；未给位置时先询问。不得自动修改代码、数据库、需求状态或安装副本。提供 ddd-domain-relationships 和 ddd-aggregate-design 的交接建议，但两者未安装不妨碍本包完成。ready_for_review 仅表示可审阅，不等于设计批准或实施授权。
