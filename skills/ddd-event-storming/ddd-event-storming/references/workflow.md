# 事件风暴执行流程（Event Storming Workflow）

## 分析约束（Analysis Constraints）

先消费同目录 evidence-contract.md。下文的方法取自课程第 03–04 讲；证据状态、稳定标识、功能覆盖矩阵、输出权限和自检停止条件属于本包工程补充。课程讲解的是协作分析，不是目标项目业务事实。

每个重要输出登记 evidence_ids 和 confirmation_status。没有证据的推断用 candidate；关键事实无答案用 unknown；相互冲突的材料用 conflicted。不得新造一个 source_id 来伪装证据。source_id 只登记本次确实读取或收到的材料。

## 1. 确定范围与方法（Scope and Method）

1. 记录本次要理解的业务过程、系统或限界上下文，以及范围外事项。
2. 记录 baseline：当前行为、已批准目标、分析材料的版本或时间、读取范围、写入范围及已有需求表达方式。
3. 建立 sources。优先使用目标项目声明的来源优先级。没有来源优先级且材料有实质冲突时，保留各方证据并提问。
4. 选择工作方式：
   - 需求不清晰或术语理解不一致：开展结果驱动分析和澄清。
   - 已有成熟用例或用户故事：保留原结构，映射事件、命令、角色、查询、名词和规则，定位缺口。
   - 业务已清楚且只要求技术架构改造：说明此方法收益有限，交付适用性判断，不虚构完整事件会。

如果缺少可访问材料或无法确定范围，返回 blocked 并说明所需输入。仅缺局部事实时，继续独立部分，受影响部分转为问题。

## 2. 识别业务结果（Business Outcomes）

按一个业务过程开始。询问“发生了什么业务结果，谁关心这个结果”。事件优先采用现有业务术语；没有既有术语时，使用清楚表达已发生结果的名称，例如“申请已提交”。动作名称如“提交申请”归入命令。

检查候选事件：

- 结果是否属于当前业务范围？若只是假想的未来场景，保留候选或明确范围外依据。
- 是否表示已发生且业务关注的变化或通知？缓存命中、事务回滚等技术结果不进入领域事件表。
- 是否只是读取信息？纯查询保留在独立查询表，不制造“已查询”领域事件。
- 名称是否隐藏重要区别？例如签订和生效可能不同，答案必须来自目标业务证据。

粒度先以业务可识别的结果为单位。不要把每次界面输入、附件上传或数据库操作都拆成事件。只有证据表明小步骤有独立业务含义时才拆分，记录拆分理由。用“对业务有独立影响”判断粒度，不用是否发送消息来强迫架构选择。

## 3. 发散与收敛（Divergence and Convergence）

领域专家和技术人员共同参与时，先分别保留理解，再比较遗漏、同义词、不同状态和规则；确认后的结论记录确认来源。没有独立参与者时，分别整理不同材料的表述，再提出候选和具体问题。禁止把角色扮演、多个 Agent 的赞同或自检写成业务确认。

使用统一术语表，记录推荐术语、已有别名、定义、适用范围、证据与待确认项。不要为了符合“某物已某动作”的格式改掉业务约定词。

给事件标记 path_kind：main、optional 或 exception，说明适用条件。主路径表示当前场景的主要业务路径，不推导所有场景都必经。可选事件、重复发生及退出路径单独保留；异常必须能对应业务后果或问题。

order_note 只描述材料支持的粗顺序。严格的先后、条件、互斥、并发和重复约束保存为规则；必要时建议另建流程或顺序视图。不要从表中相邻位置推导严格依赖。

## 4. 识别命令与附加信息（Commands and Context）

对每个事件询问：由什么操作促成，什么角色或系统发起，执行前需要读取什么数据？反推得到的新解释先作为 candidate。不要默认事件与命令一一对应；同一操作可能在不同条件下产生不同结果，外部触发也需要保留证据和未决问题。

命令记录 command_id、command、actor_roles 和 required_read_data：

- actor_roles 使用业务角色或系统，不用具体人名。多个角色的权限条件分别记入规则；角色含义不清时写 unknown 并关联 question_ids。
- required_read_data 可以有零项或多项。经证据确认不需要读取时写 none，并附证据；材料未说明时写 unknown。不要猜数据库表、API 或权限字段。
- 同一命令需要的读取需求，要登记对应 read_data_ids，供功能覆盖检查复用。
- 失败操作并非必然产生领域事件。若存在业务记录、通知或状态结果，按证据登记；否则保留异常需求，不能造出成功事件。

命令、角色或读取存在冲突时，保留 conflicted 状态及各方依据，停止依赖这些事实的设计结论。

## 5. 提取领域名词（Domain Nouns）

从事件、命令、角色和查询数据提取名词，建立 concepts。相关行为按名词分组；同一事件涉及多个名词时，复用 event_id，并关联多个 concept_id，避免复制成两个不同事件。

每个 concept 记录名称、当前含义、范围、来源及待建模问题。新提取的模型候选默认 candidate。名词可以最终成为实体、值对象、角色、属性，也可能需要合并或拆分。此处不提前定类型。

课程例子的“企业等于租户”或“管理人员是什么角色”等结论不能移植到目标项目。对目标概念的等价、差异和归属提出问题，不以代码同名、词语相近或出现频率代替业务证据。

## 6. 补齐查询与功能覆盖（Queries and Coverage）

1. 汇总命令所需读取的数据，关联具体命令和查询目的。
2. 另查纯查询：使用角色、查询问题、输出数据、筛选与范围要求，以及权限、时效等材料已给出的条件。不凭空补条件。
3. 对照当前用户故事、用例或功能清单逐项建立覆盖矩阵。coverage_status 使用 covered、gap、out_of_scope、unknown；它表示映射情况，不替代 confirmation_status。
4. 检查修改、删除、撤销、退出、重复进入和例外是否属于需求。不能因为 CRUD 看似显而易见就省略其需求登记。
5. 若事件图为了交流省略某功能，覆盖矩阵仍需指向需求基线，说明“已登记、未在事件视图展开”。若功能是否存在未知，创建问题，不默认新增修改删除能力。
6. 无完整功能基线时，明确只能检查已收到材料的覆盖；result_status 使用 needs_clarification。不得宣称需求已完整。

已有用例可以作为功能全集载体，不强迫团队长期维护第二套事件产物。按用户要求在报告中提供映射和更新建议，不自行修改现有需求文件。

## 7. 保存规则与未决问题（Rules and Questions）

统一 rules 至少包含 rule_id、statement、scope、evidence_ids、confirmation_status、question_ids。规则保留前提、例外、时间范围、精确计量口径和一致性要求；材料未提供的条件标记未知。

每个 open_question 说明缺什么事实、影响哪些事件或概念、由什么角色确认。每个 decision 区分已批准目标、分析选择、候选方案及范围排除；记录 decision_reason，但不得用理由替代证据。

不变规则及并发冲突线索可交给聚合设计；概念、角色、多种关联或时间语义问题可交给关联分析。只交接实际已分析内容，不要求其他 Skill 安装，也不宣布已完成后续设计。

## 8. 自检与交付（Review and Delivery）

按 assets/report-template.md 检查：

- 范围、基线和证据可复核，事实与候选分开。
- 技术事件与纯查询未混入领域事件，命令与结果名称未混淆。
- 事件、命令、角色、读取与概念能相互追踪，稳定标识未因排版改变。
- 主路径、可选和异常被保留，粗顺序没有升级成严格流程。
- 独立查询与功能覆盖已检查，缺口和排除有依据。
- 规则保留条件和例外，未知或冲突关联问题。
- 输出没有自动变成编码、架构决定、需求批准或文件写入。

最多两轮调整可由已有证据解决的表达和映射问题。需要新业务事实时立即停止受影响结论。按契约选择 ready_for_review、needs_clarification 或 blocked，默认在对话中交付。保存仅在用户明确要求后写入指定位置；没有位置先询问。
