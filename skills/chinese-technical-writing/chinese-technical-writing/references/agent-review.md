# Agent 写作自检（Agent Review）

## 检查方法（Method）

通读成稿，逐段问：读者能否找到具体对象、动作、条件和结果？能否追溯技术结论？发现下面的写法时逐处判断，保留确有信息价值的内容，不按词表机械替换。这里的自检借鉴 [zh-tech-writing](https://github.com/leter/zh-tech-writing) 的审稿思路；规则与示例为本包编写，两份上游指南的原文仍是主要写作依据。

| 待检查写法 | 修改办法 |
| --- | --- |
| 用“随着技术发展”“本文将介绍”开头，却没有交代文档用途 | 直接说明对象、适用读者和读完能完成的事。 |
| “功能强大”“性能显著提升”等评价，没有比较条件或数据 | 写明指标、环境和结果；无证据时删去评价。 |
| “进行配置修改”“完成接口调用”等名词化动作 | 在意思不变时改成“修改配置”“调用接口”。 |
| “该服务”“此配置”“其结果”可能指向多个对象 | 重复具体名称，消除歧义。 |
| 一句放入多个条件、动作和结果 | 按执行顺序拆句；保留前提与例外。 |
| 用排比、三项列表或设问撑起结构 | 按实际信息分段或列项，直接给结论。 |
| 结尾重复前文，或用客套话收束 | 删除重复内容；需要结尾时写明确的后续动作。 |
| 写“已支持”“已验证”，但依据只是计划或示例 | 按证据改写状态，并标明未验证的部分。 |

## 改写示例（Example）

空泛：本方案全面优化了配置管理，为开发者提供高效、便捷的使用体验。

具体：服务启动时从 `config.yaml` 读取超时值。修改文件后需重启服务，新值才会生效。

上例仅演示写法，不代表任何目标项目确有这些行为。实际文档必须先核实配置文件和生效时机。

## 交付前复核（Final Review）

1. 删除不提供事实、条件或动作的套话。
2. 检查每个短句是否仍保留必要前提；不要为了短而省掉错误条件。
3. 按包内原文的示例复核标题、句子、段落、数字和标点。
4. 再检查示例命令、链接与跨文档引用；无法核实的内容明确标注。
