# Java/Spring Boot 重构治理体系 D4 方案（Java/Spring Boot Refactoring Governance Design D4）

版本：`D4`。整合日期：2026-10-18（Asia/Shanghai）。状态：**设计已整合，实施与运行验证未开始**。

D4 完整承接 D3、D2、D1/R1 和原 Top 50 九组能力补充，保留已整合的 10 项 P2 与条件 P3，并补齐 D3-R1 剩余两项 P2：义务实例的对象身份与版本，以及子手法资格分支到用例的映射。D4 文档集是本次建议的完整设计基线；D3 及历次版本、评审保留为历史证据，不与 D4 并列定义当前行为。项目规约与用户指令仍高于本设计。本次只新增临时方案文件，不创建或修改实际 Skill。

## 阅读入口与设计结论（Reading Guide and Decisions）

保留两个核心入口：`java-refactor-governor` 与 `java-comment-governance`。结构改写、重复评估、框架审查和验证保持独立职责，先作为内部模块；性能采用主入口内的可选专项模式。未来只有出现真实独立分发需求时，才评估性能独立包。

内部仍保留 48 个操作族和 8 个专项，以及 governance/operations/playbooks/profiles/adapters 的既有职责目录。它们按实际条件加载，不拆成更多用户入口；同一子手法只维护一份具体规范。按任务意图区分事实分析、改写计划与已有对象验证，未触发的专项不生成空记录。D4 在既有主契约、操作卡和 case 索引中补字段及分支，不增加资格审核 Skill、专项或每任务必跑套件。

本设计的完整性指：当前已识别、适合采纳的能力有规则、路由、操作或专项流程、停止条件及验收设计；子手法的已映射资格分支与具体待补分支均有明确登记，不能从操作族的代表用例推导全部子手法已获资格。它不表示 61 份来源定义的所有内容都已采用，不表示未读支持文件已审计，也不表示实际 Skill 已经可用。

### 支持范围与明确分流（Supported Work and Routing Out）

普通流程处理已授权的行为保持型重构、分析、计划和文档治理。授权之外的功能修复、公开 API/schema 变化、依赖或 JDK 升级、线程模型改变、MVC/WebFlux 转换，先形成专项计划及影响说明。已有明确授权可直接消费，无须因内部模块切换重复确认。没有授权时，停止依赖该变更的写动作。

普通重构保持输入、输出、状态、副作用、异常、SQL 数据范围、事务、权限、日志指标、资源与调用顺序等实际契约。专项迁移可改变其中明确获准改变的部分，但须另记旧契约、新契约、兼容责任和验收。不能把范围变化藏在“代码更简洁”之中。

`inspection_scope`、`effective_write_scope`、`execution_envelope` 和 `evidence_scope` 分开。只读影响调查可以超出写范围；不能因此修改范围外的声明、调用方或注释。若完整目标必须修改额外位置，先交付具体位置与原因；能独立完成的已授权部分继续。

## 两个核心入口与内部职责（Two Core Entry Points and Internal Responsibilities）

| 入口 | 操作与写边界 | 独立使用要求 |
|---|---|---|
| `java-refactor-governor` | analyze/plan/apply/verify；编排内部评估、改写、文档和验证；apply 才可在授权范围改源码 | 自带完成核心流程所需的治理契约与操作参考；不依赖另装 S02/S04/S05/S06 |
| `java-comment-governance` | 注释 analyze/plan/apply/verify；独立修订类/方法 Javadoc、段落空白与行注释 | 自带可追溯的最小治理投影；不必先安装主入口；结构问题返回候选，不自行改变表达式 |

两个入口均是拟议名称。主入口的结构改写可直接消费同一 DOC 规则和 OP-47，无须嵌套调用另一个 Skill。注释入口提供专门的发现体验；其入口编排不再定义另一套 DOC 规范。若宿主选择委托注释入口，必须复用同一 context、run/task、目标集与结果所有者，避免双重 Bootstrap。

| 模块 | 单一职责及产物 | D1 职责去向 |
|---|---|---|
| M1 协调 | 解析任务/授权、确认必需义务、选路、按意图收口 | S01 |
| M2 事实与影响 | 项目画像、资产/消费者、问题与证据、影响闭包 | S01 的发现职责 |
| M3 重复与抽象 | 比较单元、语义事实、收益成本、动作/形态及就绪门 | S04 |
| M4 操作执行 | 消费 OP 与获准计划，产生最小差异和变换血缘 | S02 |
| M5 文档治理 | 文档目标、内容和段落审阅，按授权补写 | S03；两入口消费同一规则 |
| M6 生态审查 | 已确认 Spring/ORM 的专属风险与保护要求 | S05；不接管通用 Java/资源义务 |
| M7 验证 | **唯一验证计划**，义务→检查→证据；汇总当前对象结论 | S06 |
| M8 专项编排 | 按 PB 组织遗留、批量、迁移、性能等阶段 | 原横切流程及 S07 能力 |

M1 是治理结果所有者；父工作流可以担任 M1 或委托主入口，二者择一。M7 汇总验证对象结论，M1 按 operation 判断工作是否完成。主题规则维护者定义义务；M2/M3/M6 提供事实与审查；M4 报告实际触达。多个职责由同一 Agent 执行时，不声称获得了独立审核。

```mermaid
flowchart TD
    E[用户或父工作流] --> I{两个入口之一}
    I --> F[一次 context 与全匹配路由]
    F --> O{operation}
    O -->|analyze| A[事实 问题 未知]
    O -->|verify| V[已有 subject 与 required checks]
    O -->|plan| P[PB08 可裁剪计划]
    O -->|apply| P
    P --> G{已授权 apply 且前提满足}
    G -->|是| X[选定 OP 与条件 PB]
    X --> D[实际差异 文档 新影响]
    D --> V
    G -->|plan 或尚缺前提| R[M1 按意图收口]
    A --> R
    V --> R
```

图为职责与意图示意，Mermaid 未进行渲染验收。M7 维护唯一验证计划，各分支可复用已有证据。analyze/plan 不写源码，verify 不自动修复。可选工具、子 Agent、MCP、hook 和性能独立包不是核心入口必要安装前提。

## 规则载体、权威与唯一解析（Rule Carriers, Authority and Resolution）

### 维护源与视图分工（Canonical Sources and Views）

| 载体 | 唯一维护内容 | 引用方式 |
|---|---|---|
| 项目 AGENTS/CLAUDE 与 instructions | 已采用规范、范围红线、治理入口及 profile 选择 | 保持轻量，不复制手法全文 |
| 共享规则 registry 与主题正文 | rule_key、适用条件、单一规范、义务、检查要求、来源与版本 | 主包未来 canonical source 维护；DOC/DUP 等不在各包重复编辑 |
| profile | 逐模块事实、已采用规则、参数和明确覆盖 | 记录依据；不复制另一套规则文本 |
| rule set 与 route | 规则键的加载视图、触发条件、条件依赖 | 引用规则，不另立通过标准 |
| canonical operation recipe | 子手法唯一前提、步骤、特有保护性质和停止/回退；其资格分支与 case 映射 | 模式索引/别名跳转到同一 recipe，不复制特有细则 |
| playbook | 条件编排、阶段出口、专项证据和保留裁决 | 调用 OP；新增通用约束回到共享 registry |
| 包内派生投影 | 独立运行必需的共享规则子集 | 保留源版本/hash、范围、生成方式；只能从源重新派生 |
| run evidence | 本次事实、决策、差异与检查结果 | 多规则引用同一事实，不复制多份独立结论 |
| case/oracle | 验收输入和预置判定标准 | 验证规则，不凭测试预期发明新的生产规范 |

未来的源包仍遵循 `skills/<skill-name>/<skill-name>/`，主包内部按 governance/operations/playbooks/profiles/adapters 组织引用。本文附册是设计载体，不是已经创建的包文件树。注释独立包的最小投影只包含其治理和 DOC 所需内容；无主包时按已核验投影运行，不能扫描猜测兄弟目录。

项目明确要求的规则缺失时，不能通过 standalone 模式绕过。仅缺少可选项目部署目录，且已确认没有对应强制约束时，可使用已验证的内置默认 profile，记录来源与限制。安装副本、缓存和示例目录都不是新的维护权威。

### 子手法索引与加载关系（Recipe Index and Loading Relations）

操作族 ID 保留用于发现、兼容和追溯；内部子手法有唯一 `canonical_recipe`。`alias` 只解析别名，`requires` 代表选定 recipe 的必需前提，`conditional_requires` 仅在有证据的条件成立时加载，`informational` 只供进一步阅读。普通交叉引用不自动变成依赖。有效规则解析和 recipe 解析分别去重，不能因两个 OP 引用同一细则而产生两次变换。

OP-21 维护 Builder，OP-23 维护 Factory，OP-09 维护适用的 Strategy 变换，OP-48 维护 Template；OP-27 是模式选择索引。OP-45 维护性能技术候选，PB-05 只维护实验协议与保留裁决。OP-46 维护测试代码变换，PB-06 只维护证明策略和证据组织。OP-14 维护有界删除原意检查，OP-40 按条件引用。所有入口选择同一子手法时必须得到相同前提、义务及资格分支；OP ID 本身不代表支持该族全部子手法。具体技术和分支清单在操作库唯一维护，统一 case 索引只作派生。完整选择规则见[子手法资格闭包](#d4-recipe-qualification)。

### 有效定义解析（Effective Definition Resolution）

逻辑键为 `rule_key = namespace + rule_id`。在同一适用作用域，每个键恰有一个有效定义。来源链可包含多个候选，不能把 `(id, hash)` 不同就当作两个有效规则。

1. 读取宿主有效指令层级。在其约束内，按当前用户明确要求、适用项目规范、已配置规范、已采用参考和通用建议解析。
2. 先核作用域与采用声明。不同模块的明确覆盖可以并存，但本次一个作用域只能有一个有效定义。
3. 同源、同版本、同 hash 合并；保留全部命中理由。**同源同版本不同 hash 为完整性冲突**，不能选较新文件。
4. 不同版本按已声明兼容与部署映射选择；用户/项目的明确覆盖记录 `supersedes`、依据、适用范围和旧源。版本号较大不自动优先。
5. 同级无法解决的冲突、必需规则缺失、无法确认完整性，阻断依赖写动作。无关规则问题不阻断独立任务。
6. 依赖闭包按选出的有效定义计算。循环引用只去重遍历；无法满足的适用必需依赖必须报告。

规则记录至少包括 `rule_key, version, content_hash, scope, source_refs, authority, applicability, requires, conditional_requires, requirement, protected_obligations, verification_methods, requiredness, severity, override_chain`。内容维护者、评估者、验证者、结果所有者分别登记。`requiredness` 与问题严重度、改动风险分开。

### 发现与闭包算法（Discovery and Closure Algorithm）

1. 固定用户意图、有效授权、项目/模块和 preimage；列出输入资产，不限于 `.java`。
2. 用源码绑定、配置/资源、构建生成关系和消费者信息发现影响。每种方法记录查找范围、结果与盲区；工具无结果不等于消费者不存在。
3. 匹配全部路由。条件判断使用实际操作及保护语义；在 Spring 类内补注释不自动需要事务运行测试。
4. 解析唯一有效规则；求 `requires` 和满足条件的 `conditional_requires` 闭包直至不再增加。重复应用应得到同一集合，保留每条适用依据。
5. 为每个已发现影响给出 `resolved / excluded_with_evidence / base_only / routed_out / unresolved`。base_only 必须证明 CORE/TEST 已足够；unsupported/unmapped 不能判成 N/A。
6. M7 先固定不可变 subject_identity，再按有效规则、保护性质、作用域/消费者、相关 profile 和 subject 阶段形成义务实例；M1 确认必需集，再选 required_check_set。仅同对象版本、同条件的多路由合并理由；不同对象、版本或条件保留独立责任。候选对象/版本、操作、技术、消费者或作用域改变后，在**下一写动作之前**重算受影响实例。
7. 每个 slice 之后比较实际差异与计划；出现新增资产/隐式消费者/Bean/调用边界则停止依赖写动作并重新闭包。
8. 最终针对 postimage、实际资源/配置和所有必需义务再核一次。仅失效的证据重跑，无关变化不强制全库重测。

`resolved` 只表示找到了设计承接，不表示检查通过。当前支持清单之外的技术可继续只读分析或输出专项需求；只有取得可用规则、操作前提和充分证明后才能进入相关 apply。

## 重复识别与抽象决策（Duplication and Abstraction Decisions）

### 比较单元与语义事实（Comparison Unit and Semantic Facts）

先声明 `comparison_unit`：整个业务责任、稳定流程骨架，或边界明确的技术子职责；同时列出 `retained_responsibilities`。不能用两个方法中一段相似计算，推导整个业务流程语义相同。

| 候选类型 | 需要逐项比较的事实 |
|---|---|
| 相似方法 | 业务意图、输入/输出、状态、调用顺序、异常、副作用、所有者 |
| 相似查询 | tenant/权限/软删除、数据范围、绑定与 null、投影、排序分页、锁、事务、插件 |
| 相似转换 | 字段含义与方向、单位/精度/时区、null/缺省、脱敏、身份/别名与可变性 |
| 相似校验 | 规则所有者、执行时点、短路、错误顺序、错误码/消息/异常、信息暴露 |

原六项比较继续保留其目的，但分开事实与证明：意图、契约、执行语义、所有者及已知变化记录 `same/different/unknown`；`verification_evidence` 改为逐义务证据引用及 `evidence_sufficiency=sufficient/insufficient/contradictory`。证据形式不同不代表行为不同；真实变体不同不代表不能共享骨架。

template 需分别证明共享不变量、变化点输入输出和调用顺序契约。不同领域可共享已证实的纯技术单元，但领域判断、错误与权限仍留在各自调用方。存在决定性 unknown 或证据矛盾时，阻断依赖该事实的合并。

### 决策顺序与可执行门（Decision Order and Readiness Gate）

按范围→比较单元→语义→边界→收益成本→更简单替代→形态→证明顺序判断。至少比较保留现状或局部命名这一更简单选择。收益必须有具体维护后果，例如同一规则变更需要同步多处；成本包括调用跳转、依赖方向、参数/泛型/回调、生命周期、Javadoc、测试、迁移及后续理解成本。重复次数、相似度、LOC、模式数量不能独立决定抽取。

| 维度 | 枚举或内容 | 含义 |
|---|---|---|
| assessment | eligible / keep_local / defer | 分析结果；不是授权 |
| recommended_operation | retain / extract / move / delegate / inline / split | 支持建立和撤销抽象 |
| target_form | local / private_method / helper / component / template | 目标形态；defer 不是形态 |
| preconditions | 条件、负责者、状态、证据与待完成动作 | 仅有建议不视为满足 |
| implementation_gate | ready / conditional / blocked | 事实与实施准备状态；不授予写权限 |

`ready` 要求决定性语义已确认、边界成立、消费者清楚、前置证据充分、验证计划可执行。实际写动作还必须核对本次授权、执行范围和 preimage 新鲜度。可安排的非语义准备尚未完成时可为 conditional；关键语义未知、冲突或不能覆盖必需证明时为 blocked。不能以“之后补测试”把 blocked 降为 conditional 后立即改写。

| 事实 | 合法决策 | 反例与停止条件 |
|---|---|---|
| 各业务规则不同，但一段稳定技术计算相同 | 保留业务，仅评估技术 helper 或 keep_local | helper 吸收领域 flags，超出比较单元时重评 |
| 同类内一段职责有明确名称 | private_method 或 retain | 单纯按行数切割、产生更多理解跳转无收益 |
| 稳定计算有同一维护原因、跨调用方收益明确 | helper | 隐式上下文、反向依赖、参数持续膨胀 |
| 独立责任有协作者/状态/生命周期需要 | component | 为一个纯计算制造 Bean；未证明 scope/代理变化 |
| 稳定骨架有真实多种变化步骤 | template，先比较组合/委托 | 假想扩展、回调/flags 比原实现更复杂 |
| 语义相同但独立变化更合理或收益不足 | keep_local/retain | 不为“零重复”制造依赖 |
| 既有统一实现混入多个领域分支 | split/inline，必要外壳保留 | 删除兼容、真实扩展或测试 seam 未证明等价 |

每个决策绑定候选位置/hash、比较单元、保留责任、语义事实、边界、消费者、收益成本、备选、动作/形态、门与证据。没有候选时不生成空决策。新消费者或新差异出现后按影响重评；不能通过增加泛型、Map 或回调掩盖事实缺口。发现证据按 PB-03 区分 tool/manual，目标区分 discover/consolidate/reverse。人工路径复核原有界范围，不虚构 detector_run；reverse 检查边界与行为，不要求文本重复率下降。实际共享操作在 OP-15/48，反向手法在 OP-26/48，OP-27 仅提供模式索引。已有可靠替换/退役事实且影响可选深改收益时，引用 PB-07 的生命周期证据；未知不猜测，也不取消明确合规目标。

<a id="d4-docs"></a>
## 注释与文档治理（Comment and Documentation Governance）

### 目标集合和覆盖策略（Required Set and Coverage Policy）

`documentation_required_set` 是明确的声明清单，记录路径、声明身份、形成依据及写权限。目标类和全部目标方法必须有声明关联的本地多行 `/** ... */`；private、getter/setter、简单单行、新提取和目标 override 方法不自动豁免。只授权某方法时，不能顺带补全整类其他方法；整类全量治理则不能只统计本次 diff 中的方法。

类文档说明职责与必要的边界/生命周期/线程约束；方法文档说明行为、前置条件、返回、异常及副作用。标签按真实签名和语义使用；不能为 void 编造返回、为未知行为声称线程安全，也不能复制方法名凑文本。方法体内的块注释不替代声明 Javadoc。

构造器、字段、package/module 和生成产物属于单独 profile 选择。D4 建议显式构造器纳入，但不把建议写成用户已确认要求。接口方法属于目标方法时同样覆盖；接口/注解类型的类型说明单独登记。`inheritDoc` 是否可用于满足内容部分须由项目确认，但不免除目标方法的本地多行块；无法覆盖自身差异时仍补实质说明。生成代码/Lombok 应定位可写生成源头与外部契约，不手改输出，也不静默从要求中扣除；策略缺口只影响相应目标。

### 段落与复杂流程（Paragraphs and Complex Flows）

按真实阶段分段，以空行分隔，段首 `//` 说明目的。简单直观单行代码无需逐行注释；只有一个直观操作的方法不制造多余阶段。复杂核心流程与多级分支说明决策依据、顺序原因、约束和例外，不只翻译 if/switch，也不以“处理业务”一条注释覆盖整个长流程。

先判断段落组织是否足够，再决定是否提取方法。注释入口发现职责混杂时报告结构候选，不能自行改变条件或调用。结构执行新提取声明后回到 RT-01；调用处、方法头和原段落的说明均须同步，不能保留指向错误位置的注释。

### 四层验收与证据（Four Layers of Documentation Evidence）

1. **声明覆盖**：required_set 每项与本地多行块一一对应；默认仅 public/protected 的文档输出不足以证明 private 覆盖。
2. **语法与引用**：标签、签名、链接及目标工具链支持的语法有实际检查或明确审阅依据；记录检查器覆盖范围。
3. **段落与决策**：根据真实阶段/分支核对空行和行注释，允许不同正确表述；正则数量不能证明语义质量。
4. **内容与同步**：对照代码、消费者、测试或权威业务资料，证明职责、返回、异常、副作用和重构后的描述一致。

纯注释改动核对运行 token、声明关联及项目已有文档/静态 gate；不为低影响格式变化编写镜像测试。需同时检查注释是否承载编译/生成工具指令；存在这类消费时按 RT-15/16 追加义务，不能仅凭运行 token 不变声称无影响。项目没有 AST/doclint 检查器时可留下可复核审阅结果；不得声称运行了不存在的工具。

<a id="d4-obligations"></a>
## 保护义务、最低证明与风险（Obligations, Minimum Evidence and Risk）

### 义务族与作用域实例（Obligation Families and Scoped Instances）

OB-01—OB-18 是稳定义务族。`obligation_instance` 是本次可单独判断的保护责任，至少含 `instance_id, family_id, effective_rule_refs, protected_property, subject_identity, subject_stage, target_scope, consumer_scope, relevant_profile, applicability, requiredness, reasons`。旧 `subject_ref` 可作为不可变身份引用，不另存一份可冲突对象。profile 只保留影响该性质的条件；一实例可由数条有效规则共同支持。

<a id="d4-subject-identity"></a>
### 不可变对象身份与去重（Immutable Subject Identity and Deduplication）

`subject_identity` 的逻辑内容为 `kind + ref + revision_or_hash`。`kind` 使用验收章节的对象类型；`ref` 定位具体候选、计划、代码快照或记录；`revision_or_hash` 固定该对象版本。已有不可变 subject ID 能解析到三者时只存该 ID，不重复建立文件或字段。工作区路径、`HEAD`、`latest`、候选显示名称不能单独充当身份。身份规范化先解析已证实的同义引用；不能只因内容hash相同就把不同候选、用途或类型合并。

源码对象绑定实际输入清单及相关配置，范围以本次保护对象为准，不强制对全仓库计算一个使所有检查失效的hash。尚未实施的候选可绑定不可变计划/patch规格修订，不虚构不存在的postimage。设计case使用固定逻辑ref和case revision；执行前绑定实际对象版本。绑定缺失或冲突时保留具体缺口，不能将unknown作为一个通用身份合并所有未绑定对象，也不能记执行PASS。

实例去重键的完整逻辑内容为：**不可变 subject_identity + subject_stage + 有效规则定义集合 + 保护性质 + 目标及消费者范围 + 相关profile条件**。仅这些内容一致的多路由合并一个实例并保留全部理由。版本序列化/hash算法由实施schema固定，语义不可省略。阶段用于区分证明时点，不能代替对象身份。血缘A→B说明变换关系，不表示A与B是同一受评对象。

先确定必需对象/范围，再选证明。不能根据“手上只有A的证据”缩小必需集，也不因列出多个备选就默认全部备选必须执行或通过。只有任务明确要求A+B都满足时，二者共同构成完成条件。不同配置、性质、对象或版本保留独立实例；不按每行代码机械拆分。

每个check用 `covered_instance_refs` 声明覆盖，并能逐实例定位输入身份、配置、范围和oracle。一次组合检查可支持多个对象/实例，但每项结果仍可单独判定；不能用一个无成员映射的PASS覆盖未验证对象。证据只覆盖实例的一部分时保留缺口，或在执行前拆分明确子实例；不把局部PASS放大。

需要集合结论时，`primary_subject` 引用不可变集合manifest：列成员identity/版本、各自scope、实例映射及本次汇总目的。只有类型一致且确为同一代码结果集合时才能用相应代码kind；代码、计划、授权等异类对象使用治理记录及各自supporting verdict，不伪装成同一代码对象。成员或版本变化使manifest版本变化，不能复用旧集合结论。单对象任务无需创建集合manifest。

| 条件 | 实例与证据处理 |
|---|---|
| 同对象/版本、同规则性质/scope/profile/stage，三路由命中 | 一个实例、三个理由；同一充分检查不重复跑 |
| 同模块/路径/profile/stage，候选A与B的ref或版本不同 | 两个实例；A PASS不覆盖B NOT_CHECKED；若目标要求两者，整体apply不completed |
| A/B模块使用同规则，tenant插件不同 | 保留原D3的两配置实例；新身份规则不取消相关profile维度 |
| B变为B2 | 新身份及相应新实例；保留旧结果历史，仅重新获取受影响证明 |
| 一个检查真实覆盖A+B | 一次执行、分别覆盖、分别结论；集合汇总引用不可变成员清单 |

B→B2后，旧证据不会直接变成新实例PASS。若影响分析确认某证据的受测内容、相关配置、消费者与oracle均未受变化影响，可在既有验证记录中补充复用依据及新实例覆盖引用，经过当前覆盖核对后复用；无需新独立报告或重跑无关检查。不能证明不受影响的证据标NOT_CHECKED并补取。证据复用改变的是覆盖关系，不抹去其原始执行对象和结果。

### 义务到检查的映射（Obligation to Check Mapping）

下表定义义务族的最低证明方向。具体实例还应引用 OP/PB 中的前提和反例。每个适用必需义务至少有一个充分的检查组合；同一证据可以支持多个义务，但须明确它实际覆盖的对象与条件。M7 维护映射，M1 确认范围，M6 只追加生态条件。

| 义务 | 保护对象与最低证明 | 不能单独作为证明 |
|---|---|---|
| OB-01 | 当前授权、文件/块、执行副作用与实际 diff 一致；已有变化可区分 | 计划中写“只改目标” |
| OB-02 | 有效规则唯一、全部影响有路由裁决、闭包与逐规则适用条件可重现 | 已读若干规则文件、关键词匹配 |
| OB-03 | 文档 required_set 与四层审阅；纯文档语义消费未变 | doclint exit 0 或注释数量 |
| OB-04 | 符号绑定、重载/调用方、反射/SPI/资源/名称消费者清楚；必要加载/契约检查 | 文本替换成功、搜索零结果 |
| OB-05 | 求值次数和顺序、短路/循环/返回/异常、副作用不变量；对应边界/失败轨迹或操作特定等价证明 | 编译通过、返回值碰巧一样 |
| OB-06 | 对象身份/别名/equals-hash、可变性、字段意义/null/精度/序列化；对应输入输出及身份行为 | 字段名称相同、能反序列化一次 |
| OB-07 | 内外调用签名、二进制/HTTP/RPC/错误契约和消费者；兼容/契约测试或明确迁移证明 | 只编译当前模块 |
| OB-08 | SQL参数/数据集合、tenant/权限/软删除、投影/排序分页/锁/事务、实际 ORM 插件；已配置语义下的 fixture/查询与必要数据库证据 | mock Repository 成功、SQL文本看似一样 |
| OB-09 | 实际 Bean 装配、身份/scope、代理调用链、事务/回滚/AOP/生命周期；受影响的上下文/集成路径 | 只验证 mock 方法被调用 |
| OB-10 | 鉴权与负向路径、错误信息暴露、日志/审计/metrics/tracing 字段时机与脱敏；契约和适用负向观测 | 成功请求一次、无可见异常 |
| OB-11 | 外部协议/超时/重试/幂等、cache key/TTL、消息路由/顺序、scheduler 条件；替身契约及必要集成/失败路径 | 单纯减少外部调用次数 |
| OB-12 | 锁/可见性、任务所有权、执行/取消/中断/关闭/背压；受影响的受控并发与资源失败检查及审阅 | 普通单元测试全绿、一次耗时 |
| OB-13 | 测试目标发现、fixture 事实、隔离/seam、故障注入、断言强度；前后可检错能力 | 测试数更多或重写期望后变绿 |
| OB-14 | build/生成源→输出→打包/发现链、资源描述符、工具配置和消费者；可重现生成/编译/加载检查 | 只改生成文件、只编译源码 |
| OB-15 | 性能目标/环境/负载/样本/噪声可比、行为另证、事先确定判定及容差 | 无基线的单次更快、现代语法 |
| OB-16 | 迁移阶段权威、兼容承诺、消费者/发布状态、退役与回退条件 | 新路径可用就删旧入口 |
| OB-17 | 比较单元、语义与边界、真实变化和维护收益/成本，证据充分性；反向抽象同样检查 | 重复率降低、同名同结构 |
| OB-18 | preimage→计划→实际patch→postimage 血缘、规则/config/environment与证据匹配，命令实际覆盖目标 | 过期输出、exit 0但零目标测试 |

未知适用性不能判 N/A。没有自动化工具时，明确且充分的人工证据可以满足允许人工判断的项，例如文档业务说明、边界职责、机械前提；不能用泛泛人工认可代替必须观察的事务、数据库或并发运行性质。

<a id="d4-review-evidence"></a>
### 条件独立审查证据（Conditional Independent Review Evidence）

独立审查仅在用户明确要求、项目既有 gate，或本次已选且有具体风险依据的策略要求时进入 M7。风险等级不自动触发全部审核。主题规则确定它的 requiredness；PB-06 只负责编排与父流程移交，不复制以下契约。

`review_evidence` 最小内容为 `trigger_ref, purpose, subject={kind,ref,scope,hash}, implementer_ref, reviewer_ref, independence_basis, finding_refs, dispositions, conclusion, evidence_refs, freshness_scope`。可以引用父流程已有审查及发现处置，不必生成另一份报告。独立性须有可核事实；同一执行者改角色自述不满足。这里不指定模型、会话、轮次或额外 commit。

消费前核对目标版本/hash、范围、审查目的、独立性与必需发现处置。充分且当前的父结果直接复用，不重复请求已有授权。相关目标变化使对应审查证据失效；按影响重评，不把与目标无关的变化当全量复审理由。审查结论与代码运行证明分开；review PASS 不能替代需要运行观察的事务/数据性质。

无可用审查能力时记录移交负责方与具体缺口，审查实例为 NOT_CHECKED；移交不等于完成。必需审查未满足阻止依赖 apply completed；可选审查按已选策略记录限制。发现被接受为例外须有项目允许的依据，不由执行者单方将必需 FAIL 改为 WARN。

### 机械证明的限定条件（Limits of Mechanical Evidence）

机械证据只在操作定义允许、前提全部成立时使用。文档/空白须证明有效代码和消费注释的工具含义未变；局部符号 rename 须证明绑定与隐式名称契约不变。extract/inline 必须逐项处理自由变量、别名、求值、异常、同步与资源范围，不能仅看 AST 形状。

将多次调用缓存为一次、删除实参、交换条件或循环、改变构造/代理/事务路径，都不能自动视为机械等价。可复核证明必须列出具体操作假设和反例排除依据。若某义务仍缺证据，记 NOT_CHECKED，并采用 PB-01 建立安全网或停止依赖写动作。无既有测试不意味任意改写，也不意味永远无法开展最小准备。

### 风险与最低充分验证（Risk and Sufficient Verification）

| 风险 | 典型影响 | 验证原则 |
|---|---|---|
| R0 | 确认无语义消费变化的文档/空白 | 文档与实际差异；已有项目必需 gate |
| R1 | 已知消费者内的局部结构 | 绑定/类型与操作对应行为；机械证据须满足上文限定 |
| R2 | API/DTO/数据/框架/安全/外部边界 | 对应专项审阅和契约/集成证明 |
| R3 | 跨发布消费者、关键并发、较大事务影响或性能实验 | 专项阶段、可重现环境/结果、分步及恢复条件 |

风险取实际影响，不按行数或所在文件机械判定。决定性影响未知单独标 unresolved。无需每个任务执行全部测试，但项目既有明确 gate 不能静默删减。既有无关失败只有在已采用隔离契约允许且本次义务充分证明时才可单列；仍属必需项的失败不能用 WARN 降级关闭。

<a id="d4-evidence"></a>
## 执行生命周期与证据血缘（Lifecycle and Evidence Lineage）

### 标准执行顺序（Standard Execution Sequence）

1. 固定 operation、目标、已有授权及一次 context，记录工作区已有变化。
2. 取得本次所需画像、资产/消费者、规则来源和 subject 基线；未知按依赖标注，不要求所有无关技术都调查完。
3. 全匹配路由，解析有效规则与所选 recipe，按影响实例化保护义务。M7 建立唯一验证计划，明确当前需要的证据。
4. 按意图分支：analyze 产出事实/问题/未知；verify 固定已有对象及约定检查；plan/apply 才消费 PB-08。只有候选共享/撤销时运行抽象判断，只有排序/收益需求时运行 PB-07。
5. 仅为相关义务采集 baseline、检查执行 envelope。行为证明不足才选 PB-01；充分机械证明可用时不强造业务测试。analyze/plan 在约定交付齐全后收口，不因尚未执行未来实验而伪装 apply。
6. apply 检查授权、前提与输入新鲜度后执行闭合 transformation_unit；单一单元复用 single_slice 最小记录，真实批量才进入 PB-02 batch。逐步记录差异、新声明与消费者，下一依赖写入前重评新增影响并同步文档。
7. verify 或 apply 的验证阶段执行 required_check_set，核对目标身份、实际覆盖与结果；按需消费父审查和专项证据。失败、缺口和无效证据如实保留，只有受影响的证据需重取。
8. M1 按 operation 收口，保留 primary_subject 与各 supporting verdict 的对象边界，报告未完成必需实例；父流程独立判断其整体交付。

analyze 只需判断事实时不强制形成改写备选；verify 缺某项前提只补该项，不重写整份 PB-08。任何新写动作仍须落在现有授权内。

### 变换前后证据关系（Transformation Lineage）

决策绑定 `preimage A + planned_transformation P + assumptions`。执行记录绑定 `A → actual_patch → B`。每个对象先按不可变subject身份区分，再记录血缘；血缘不用于实例去重。后置审阅和测试绑定 `postimage B + effective_rules + relevant_config + environment`。

- 执行前 A 被外部改成 A2：依赖旧 A 的决策不可直接使用，先重评。
- 获准且符合计划的 A→B：核对血缘和后置条件，不因预期变换导致 hash 不同就循环重做全部前置判断。
- 实际 patch 超过 P，或破坏假设：下一依赖动作前重路由/重评。
- 对 B 验证后又改成 B2：创建新身份及相应实例，受影响证据失效；不能直接沿用 B 的结果。未受影响证明按[对象身份契约](#d4-subject-identity)核对覆盖后复用。
- 不相关模块改动：记录理由，复用仍有效的证据，不强制全库重跑。

run、slice、rule、obligation、check、evidence 与 source_ref 使用稳定 ID 和相对引用。证据保留实际结果，不仅保留生成者的总结。前后 SQL/轨迹/golden 可用于差分，但不得把新结果自动写成新的正确基线。

### 停止、失败与恢复（Stops, Failures and Recovery）

关键事实/规则/授权/执行范围不成立时，停止依赖写动作并给出具体缺口；独立分析和授权部分可继续。出现明确回归时标 FAIL，停止相关后续步骤，在授权内修复或恢复本次拥有的差异，再验证。恢复不是工作区 reset；重叠用户变化无法安全分离时停止覆盖恢复。

不得为获得通过而改业务要求、错误码、SQL含义、权限、测试期望或断言。可提议独立修复任务，但当前保留真实失败。工具不可用、索引过期、测试被跳过或环境不具备须报告 NOT_CHECKED；可以选择能提供同等证明的已有方式，并说明替代范围。

<a id="d4-acceptance"></a>
## 状态、验收与完成条件（States, Acceptance and Completion）

### 四个独立维度（Four Independent Dimensions）

`operation=analyze/plan/apply/verify` 表示用户意图；`phase=discover/classify/plan/apply/verify/close` 表示当前阶段；`activity_status=not_started/running/blocked/completed/failed` 表示活动执行；`object_verdict=PASS/FAIL/WARN/N/A/NOT_CHECKED` 表示受评对象结论。

`outcome=changed/no_change/kept_local/deferred/routed_out` 另记实际结果。每个 check/verdict 必须声明 `verdict_subject={kind,ref,scope}`：kind 可为 `code_baseline`、`code_postimage`、`proposed_transformation`、`refactoring_plan`、`governance_record` 或 `measurement_comparison`；ref 必须解析到[不可变subject_identity](#d4-subject-identity)及实际版本/hash，scope 声明被检查的范围；集合对象遵循该处manifest和成员映射规则。对象不得在汇总中暗换。治理总结果用 `primary_subject` 明确本次主要回答的对象，`object_verdict` 只对应它；`supporting_verdict_refs` 可以引用前置授权、基线、计划、审查等其他对象结论，各自保留 subject/status。历史字段 `governance_result.verdict_subject` 仅可作为 primary_subject 的兼容别名，不能同时填写不同值。

例如拒绝整体合并时，对 `proposed_transformation` 的结论可以是 FAIL；对包含正确拒绝理由的 `refactoring_plan` 可以是 PASS。两者必须在记录和展示中注明对象；计划 PASS 不证明候选或代码通过。执行计划成熟度另用 implementation_gate，不能由对象结论自动推导。

既有必需 gate 失败时，失败绑定被实际检查的 code_baseline/code_postimage 及 gate identity，apply 为 blocked；候选行为未受检就保留 NOT_CHECKED，不能把旧失败归因候选回归。若评的是候选资格，scope 明确 eligibility 及违反的准入规则。候选行为 FAIL 需要直接违反证据：可以是受控运行，也可以是前提充分的可复核语义证明，不要求先执行明显错误的候选。

| operation | activity_status 可为 completed 的条件 | 对象和权限边界 |
|---|---|---|
| analyze | 约定范围已分析，问题/事实/建议/未知与理由齐全 | 可以 completed+FAIL（如查出缺 Javadoc）；不要求先修复 |
| plan | PB-08 计划内容完整，待决条件、所需范围、证明和恢复可核对 | 可有 conditional/blocked；计划完成不授权 apply |
| apply | 授权目标全部满足；全部适用必需项 PASS 或有证据 N/A；无必需冲突/未验证项 | 必需 FAIL/NOT_CHECKED 时不能 completed；保留 progress 与具体阻塞 |
| verify | 完成约定检查或允许的尝试及缺口报告 | 可 completed+FAIL；环境不可用且约定尝试已完整完成可 completed+NOT_CHECKED，否则活动仍 blocked/failed |

analyze/plan/verify 中发现对象失败，通常不是活动 failed；只有执行故障或约定动作未完成才用相应活动状态。父流程必须读 operation、对象结论和必需缺口，不能只看 completed。

单项 status：PASS 为有当前对象与实际覆盖的充分证据；FAIL 为发现违反；N/A 须证实适用条件不成立；NOT_CHECKED 为未执行、不可用、不足或过期；WARN 只用于非阻断建议。只汇总同一声明对象/版本内可映射的义务，不能用计划检查覆盖代码缺证据。对象汇总：适用必需 FAIL→FAIL；否则有必需 NOT_CHECKED→NOT_CHECKED；必需项满足且有允许的非阻断限制→WARN；其余→PASS；整个域确实不适用才→N/A。已确认代码缺文档时，该合规对象为 FAIL，即使写入另因范围不足而 blocked。

### 按意图适用的完成清单（Intent-Specific Definition of Done）

| 检查 | analyze | plan | apply | verify |
|---|---|---|---|---|
| 意图/范围/画像/来源与未知清楚 | 必需 | 必需 | 必需 | 必需 |
| 实际影响有路由裁决 | 在分析范围内 | 计划影响完整 | 实际差异闭包完整 | 受测对象与约定义务完整 |
| 抽象/边界判断 | 有候选时给结论与证据 | 有共享/反向候选才给比较单元/动作/门 | 适用决策有效且执行未越单元 | 仅核当前对象需要的决策及证明 |
| 文档 | 识别缺口，不要求修复 | 声明目标与补写步骤 | required_set 全部满足 | 报告真实合规或失败 |
| 实施与差异 | 不写源码 | 不写源码 | 目标完成、授权内、血缘齐全 | 按明确 verify 范围执行，不自动修复 |
| 验证 | 不虚构运行；指出需要的证明 | 义务→检查/前提/范围已定义 | 适用必需证据充分且新鲜 | 完成约定执行/尝试与真实报告 |

### 两套选择集合与可判断验收（Two Selection Sets and Decidable Acceptance）

原 AC-01—AC-32、111个CASE-D2、16个CASE-D3、146个OC及24个CASE-PB的稳定ID全部保留。D4新增6个CASE-D4-R01—R06，以及4个含结构化变体的Builder/Factory技术用例：OC-21-BP/BN、OC-23-FP/FN。统一[设计case索引](java-springboot-refactoring-governance-d4-cases.json)共307个标识，其中133个治理/修订正文、150个OC、24个PB。标识和变体数不是独立执行次数或覆盖率；执行必须绑定case revision及当前D4契约。

索引按每个用例的实际责任记录适用条件、OP/PB/RT/规则/义务族关联、逻辑 subject、独立 oracle、期望动作/状态、验证层以及可复用的 scenario/check 关系。无关联字段应明确不适用理由，不能为凑覆盖填所有规则。验证层描述被证明的性质，例如治理决策、代码行为、文档语义、adapter、host 或测量；NOT_RUN 描述执行状态，不能代替验证层。

| 集合 | 用途与选择 | 不能混淆 |
|---|---|---|
| qualification_case_set | 对将来实现的 Skill/recipe/adapter 作资格验收；根据宣称支持的 recipe、分支和宿主选对应正反例，关键拒绝分支不能只用通用 AC 代替 | 尚未绑定 fixture 的设计反例不记运行 PASS |
| required_check_set | 对当前工程任务的义务实例选择最低充分检查，引用既有适用证据；机械证明与人工内容审阅按义务允许采用 | 不把 307 设计用例及其变体全部变成每次改名/注释任务的固定测试 |

先固定逻辑对象、性质和期望，再绑定实际 fixture hash、JDK/框架/模块/数据库、命令与隔离资源。每个执行 case 具有 operation/授权/刺激、前置、预置 oracle、期望与实际证据、清理；被测 Skill 自述不作 oracle。只读正确拒绝是治理决策证明，不能当成 Java 行为运行通过。

一个 SPI 场景可同时关联操作、专项与治理 case，但每条关联必须说明证明角色和充分范围；不能把同一证据计作几次独立行为证明，也不为了关联数重复运行。case 选择闭包检查和真实义务证据闭包分别执行。零目标测试、错误模块/profile、skip 或过期输出不能满足 required_check_set。

本轮 case 的执行状态全部 NOT_RUN。文档/索引静态检查、设计推演、包级 lint、宿主触发、Java/数据库/事务/并发/性能运行验证分别报告。

<a id="d4-recipe-qualification"></a>
### 子手法资格闭包与支持边界（Recipe Qualification Closure and Support Boundary）

操作卡是子手法技术规范与资格分支的唯一维护源。它登记 `canonical_recipe_id`、支持变体、必要性质/分支、适用条件、`case_id + variant_id`、证明角色及待补理由；统一索引派生相同关系，不能在索引独立修改技术规则。一个case或变体可证明多个性质，一条性质也可由几个检查组合证明，不按每项字段强制新增fixture。OP-27别名复用owner的同一资格分支，不另存第二套。

先区分设计映射状态与实际资格结论：`mapped_in_design`只表示有明确逻辑用例及oracle；`qualification_pending`表示该具体分支/支持范围仍缺规格或映射，须列缺口；当前运行一律NOT_RUN。设计映射完成不等于实现qualification PASS。来源采用状态和资格状态也分开：某原则adopted不等于所有工具、变体或项目环境已获资格。

资格验收按以下顺序执行：

1. 固定实现版本、recipe规格版本及声明支持的canonical子手法/变体。只写OP族不能推出支持所有子手法；不清楚时报告声明缺口。未声明的子手法不自动纳入本次资格目标。
2. 将别名解析到owner，再按入口语义与明确支持声明确定具体变体，加载该范围的必要性质及正反分支。一个owner有多变体时，缺失或含混不得猜选，也不得退回另一个已mapped变体；例如State不借Strategy通过资格。适用性unknown留缺口，不以未绑定fixture为理由删除关键分支。声明扩大时重算受影响分支。
3. 按 `case_id + variant_id + 证明角色` 求覆盖。加载一致性/正确分流等治理证据不能代替技术行为性质；参数对象用例不自动替代Builder，CQS用例不自动替代Factory。仅同目标、同性质和充分范围可共享证据。
4. 缺case映射或处于qualification_pending时，输出具体分支及所需oracle，不能宣称该实现能力通过。逻辑分支齐全后才绑定真实fixture/hash、目标工具链、环境及执行范围；未执行/不可用保留NOT_CHECKED，不借文档检查通过取代。
5. 实际资格结论按声明支持范围汇总，保留失败和未证部分；只支持CQS的实现无需声称支持Factory，别名不增加重复执行。

Builder/Factory的具体正反变体集中在OP-21/23，覆盖已有构造和创建协议的必要性质。其他已具名手法复用已有充分分支，未覆盖部分在各owner明确待补；不能因父OP有代表用例就默认通过。新recipe只在确实选入支持声明时补登记，不预建无穷变体目录。

`qualification_pending`限制相应实现能力的资格声明，不扩大成所有真实工程任务的新前置测试。实际任务仍按不可变对象和义务实例形成 `required_check_set`；人工分析、计划或已获准的操作用本次充分证据判断。具体工具能力未确认时按既有GOV-05停止依赖该能力的动作，不能把未核自动转换冒充可靠能力。普通注释、改名和参数对象任务不因此运行Builder/Factory全套资格fixture。

### 最小证据包（Minimum Evidence Package）

复用父工作流已有记录，不强制每次新建大量文件：context、rule_resolution、impact_map、必要decision/plan、实际change_record、documentation_review、verification_report、governance_result。证据可一处保存多处引用；无候选不生成空抽象报告，无运行不填虚构退出码，无修改不制造 patch。analyze/verify 不强制 plan，manual 不填 detector_run，single_slice 不造空 pilot/expand，未触发独立审查不造 review_evidence。

必须报告测试目标身份、数量与跳过情况。exit 0 但零目标测试、错模块、错误 profile 或 skip 不满足行为义务。已有失败前后分别保留。纯文档可用适用文档/静态检查，不硬造业务 RED/GREEN 循环。

### 采纳状态的语义（Meaning of Adoption States）

| 状态 | D4 含义 | 执行前的动作 |
|---|---|---|
| adopted | 主要可迁移原则或操作已纳入设计，有具体落点 | 按本次 profile/授权/证据门执行；不是预先授予 PASS |
| conditional | 能力有价值，但需版本、宿主、资源、风险或专项授权条件 | 明确资格记录和启用条件，满足后才应用 |
| excluded | 来源做法不作为本体系默认要求，有具体冲突/范围/成本原因 | 保留来源与理由；任务将来明确需要时可重新评估 |
| pending_evidence | 来源深度或事实尚不足，当前不能承诺采用范围 | 列出待读文件/待核事实；不能用臆测填成覆盖 |

复合能力可拆 facets：例如通用影响分析已采用、特定图谱协议条件采用、自动提交排除。逐项理由见[逐能力登记](java-springboot-refactoring-governance-d4-adoption.json)。登记保留 prior_coverage，不把当轮23/38的历史核心判定改成当前版本性能指标；记录数量不等于精确覆盖率。

### 条件采用清单（Conditional Adoption Register）

| 条件能力 | 采用理由 | 启用条件与未满足时处理 |
|---|---|---|

| Spring/ORM/Web/Reactive 具体 recipe | 保护或改善真实框架协作 | 对应模块技术与配置确认、实际调用/数据路径可验证；未知不套用其他 ORM 的规范 |
| 克隆/图谱/语义改写工具与外部 recipe | 可降低候选发现和批量执行成本 | 工具版本、Java支持、输入输出/副作用、索引新鲜度、许可和环境已核；可用人工/现有工具提供等价证据，否则报告限制 |
| helper/component/template 与设计模式 | 有真实责任、共享知识或变化压力时提高维护性 | M3 语义、边界、收益和更简单替代通过；否则 keep_local 或 reverse |
| golden master、依赖切断和机械准备 | 建立遗留代码的当前行为安全网 | PB-01 的最小范围、机械前提、隔离与首个基线人工核对；业务字段不归一丢失 |

### 明确排除的默认做法（Defaults Deliberately Excluded）

| 排除项 | 原因 | 保留的可迁移目的 |
|---|---|---|
| 固定 LOC/参数/复杂度/重复次数强制门槛，必须至少抽取一次、追零重复 | 会推动无价值改动和越界抽象 | 作为发现信号；最终由具体责任与净收益决定 |
| 固定 Java/Boot/构建工具、ALWAYS 构造器注入、所有 DTO 转 record | 不能代表目标事实，可能改变框架/数据行为 | 版本资格与实际项目 profile 下选择 |
| 删除全部显然注释或省略 private/简单方法文档 | 与本用户强制 Javadoc 要求冲突 | 简短但有事实的信息；简单行不机械逐行复述 |
| 自动 commit/reset、强制清空工作区、默认 GitHub issue/消息发布 | 超出普通任务授权，可能覆盖用户内容或外发 | 小步可追溯计划与本次差异记录；外发需明确指令 |
| 固定 Agent 名、模型、MCP/隐藏目录或完整安装所有市场 Skill | 宿主相关且增加依赖，未证明适用于目标 | 中立契约与可选 adapter；按真实能力调用 |
| 非 Java 专属语法/脚本、固定“10文件”文本改写策略 | 语法与类型/消费者保护不匹配 | 迁移语言无关的发现/试点/回退目的 |
| 一律继承、一行 wrapper 必删、单实现接口必删 | 忽略领域、扩展、兼容、代理与测试责任 | 真实变化点与反向抽象评估 |
| 立即删除全部兼容层或永久保持双份权威 | 消费者未迁完或长期双写会制造不一致 | 明确阶段权威、兼容窗口和退役证明 |
| 借普通重构引入新功能、schema/API/依赖升级、线程模型变化 | 属于不同用户目标与风险范围 | 识别后转具体专项；不排斥未来获准的价值 |
| 未读 references/rules/scripts 等同已覆盖，未审许可整包复制 | 缺乏证据，无法承诺能力或再分发边界 | 保留待核清单和最小来源引用 |

### 来源缺口与实施待绑定项（Remaining Source and Implementation Conditions）

原主裁决数保持 adopted 223、conditional 21、excluded 52、pending_evidence 4，不能换算为覆盖率。4 个待证条目仍为 SRC-16-CAP-04、SRC-20-CAP-03、SRC-38-CAP-05、SRC-54-CAP-03。D4 为每条能力新增d4_adoption目标映射与修订说明，保留prior_coverage、d2_adoption和d3_adoption原值；未读的深层支持文件继续 pending_evidence，不视为 D4 自动承诺的功能。各操作卡登记的qualification_pending分支、工具精确协议、目标项目实际版本/配置、宿主安装与误触发、case绑定、构造器/生成源文档策略、severity映射、证据保留路径仍需在对应实施阶段确认；不能据此取消已确定的对象身份和分支覆盖契约。这些条件不妨碍本次设计交付，也不能在真实 apply 中被忽略。

## 父工作流接入与分发（Parent Workflow Integration and Distribution）

直接注释任务进入注释入口，结构任务进入主入口。父工作流由一个 coordinator 管理 context；已有 run 可继续，不重复 Bootstrap。缺少独立 S04/S05/S06 安装不应阻止主包内部消费模块。内部参考消费要如实记录，不能称为实际 Skill 调用。

SpecLite 接入仅是方案：persona/菜单保持轻量；在加载项目上下文后建立治理 context；每个 task/subtask 实施前路由和绑定验证；验证阶段汇总当前差异义务；完成阶段记录 loaded rules、保护面、命令结果和未验证项。原资料中的 Step 2.7/7/9 是参考定位，实施前核对真实引擎，不能当作已存在接口。

Story/tracker 状态始终由父工作流拥有。治理 completed、PLAN_READY 或安装目录存在均不等于 Story 实施授权或整体完成。hook/CI 可提醒和汇总，不授予额外写权限；事件按 run/task/source/event key 去重，避免重复调用覆盖最新状态。

版本至少区分治理契约、规则内容、入口包、部署映射和 run evidence。派生投影保留 source revision/hash 和投影范围；上游规则改动后重建受影响投影，不能在安装副本手工修补后倒称 canonical source。包级格式与治理规则是两个契约；skills-lint 通过不证明 Java 行为通过。
