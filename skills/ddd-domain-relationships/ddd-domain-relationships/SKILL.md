# 领域关系分析（Domain Relationships）

## 目标与边界（Overview）

帮助业务与技术人员确认“哪些概念通过什么关系连接、在什么条件下连接多少个、关系怎样随时间变化”。适用于新需求、既有模型审阅和代码与业务描述的关系差异分析。这里只读分析并提出候选，不修改代码、数据库、需求状态或既有模型；要求保存时按用户授权位置交付。

本包采用 `base`，目标宿主为 `unspecified`，无需 MCP 或专用脚本。不依赖本机课程目录、外链图片或其他 Skill 已安装。课程方法的来源及工程补充见 [来源说明](references/source-provenance.md)。

## 输入与产出（Inputs and Outputs）

输入为业务范围、上下文、资料版本或时间、已知概念及规则、可访问的需求/决策/模型；代码和 schema 可用于核对当前行为。有上游产物时复用 `concept_id`、`rule_id`、`source_id`、`question_id`，不重新编号。名词清单只提供候选，不要求每个名词都变成实体。

产出包含双向多重性、两端角色、关系属性、时间范围、限定符、规则及证据、未决问题和实现影响候选。共同字段为 `scope`、`baseline`、`sources`、`concepts`、`rules`、`decisions`、`open_questions`、`result_status`。使用 [报告模板](assets/report-template.md) 组织结果；默认在对话中交付。

## 执行流程（Workflow）

1. 开始时读取 [证据与交接契约](references/evidence-contract.md) 和 [详细工作流](references/workflow.md)。锁定范围、上下文、版本及授权，区分当前行为、已批准目标与候选；记录材料缺口及来源冲突。
2. 澄清概念是实体/值对象候选、角色、属性、操作、类还是实例。区分实例之间的关联与类之间的泛化；只有相同字段或名字相似，不能证明存在业务关系。
3. 为每条有独立业务含义的关联逐一问：一个 A 最少/最多对应多少 B，一个 B 最少/最多对应多少 A。明确读向及当前、同时或历史范围；无答案填 `unknown` 并提问，不能由数据库外键推断业务基数。
4. 对同一对概念分别保留不同角色的关联；检查自关联的角色、根节点和循环等约束。根节点数量、上级是否必需、组织是否只能有一个，都由本次业务证据确认。
5. 判断属性属于单个对象还是关系本身。有关系属性、历史或独立业务身份时提出关联实体候选；检查有效期、退出后再次加入、同时性及重叠规则。限定符用于局部键范围，不能替代时间段不重叠规则。
6. 检查属性与关联的等价表达：保留角色、类型、多重性和规则。画图省略不等于业务约束消失；发现重复表达先说明同义/冲突及候选调整，不擅自删除用户既有图。
7. 用自然语言双向解释每条关系，以命令或业务例子走查规则；依模板交接。完成前使用 [行为用例](references/behavior-cases.md) 的失败信号自检，静态阅读不算执行了用例。最多两轮定点调整，仍需新事实时转入澄清。

## 澄清与交接（Notes）

事实/决策状态严格使用 `confirmed`、`candidate`、`unknown`、`conflicted`、`rejected`；按共同契约判断，不以 Agent 自评确认业务。关键未知或冲突阻断依赖它的结论，独立部分可以继续。结果使用 `ready_for_review`、`needs_clarification` 或 `blocked`，不表示模型批准或实现授权。

不得因一对一就合并概念、把关系属性随意塞入任一实体、用 `(A, B)` 唯一性否定合法历史，或把一对多直接划为同一聚合。聚合边界需要生命周期、不变规则与一致性分析；`implementation_implications` 只记录待评估影响，不生成 DDL 或代码。
