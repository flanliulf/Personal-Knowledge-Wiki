# D5 验收与资格输出契约（D5 Acceptance and Qualification Output Contract）

版本：`D5`。日期：2026-11-17。本文承接[主方案](方案.md#d5-acceptance)，是逻辑规格；全部被测实现与技术用例均 `NOT_RUN`。本轮没有创建 fixture 或运行 Java/宿主验证。

历史 307 个 case 的完整 JSON 未恢复。D4 验收正文只恢复 165/390 行；本册列出恢复的用例和本次 P3 条款，不伪造其余对象、关联或 oracle。原编号保留，不能把缺失记录悄悄删出声明能力的必要分支。

每例固定逻辑受评对象 `verdict_subject={kind,ref,scope}`、前提、动作和预期状态。实际执行前只补真实版本/hash、fixture、配置和命令，不临时换对象。fixture 与独立 oracle 先由验收方固定，不能把被测 Skill 的自述作为结论。表中 `PASS/FAIL/NOT_CHECKED` 是将来的预期对象结论；本轮执行状态一律 `NOT_RUN`。

基线、候选实施资格、候选行为、改后代码、计划和测量分别判断。已观察的基线失败不能自动归因为候选行为回归。针对候选的直接违反证据可以是受控运行观察，也可以是前提充分的独立语义证明；不必为证明明显错误而先执行危险候选。正确拒绝候选可形成计划 PASS，但不使候选或代码 PASS。执行故障也不自动等于代码 FAIL。允许结果引用多个 supporting verdict，保留各自对象，禁止跨对象混成一个结论。

每例绑定当前指令、可写范围、必要 profile/rule 版本与hash；故意 unknown 的前提保留。命令、允许产物、资源、副作用和清理按 `execution_envelope` 登记。analyze/plan 不改源码，verify 不自动修复，apply 仅改获准范围并保留用户变化。治理用例可以注入已说明的受控检查结果，但不得把这种输入注入宣称为真实Java运行。

## 两套选择集合（Two Selection Sets）

| 集合 | 使用时点与输入 | 选择与完成条件 |
|---|---|---|
| `qualification_case_set` | 将来实现治理核心、canonical recipe、adapter 或 host 后验证其资格；输入实现版本、声明能力及适用分支 | 选择相关治理/OP/PB/宿主正反分支；关键拒绝分支不能因fixture未建而悄悄删掉。未适用有理由，缺绑定标NOT_RUN；各层分别通过才证明对应能力 |
| `required_check_set` | 一次实际工程任务；输入已实例化义务、subject/消费者scope、profile、阶段与风险 | 为各必需实例选择充分证明。可复用机械证据、已有适用测试、人工内容审阅或组合检查；不强制每次重构跑所有资格反例 |

最小选择顺序：先确定本次是实现资格验收还是工程任务检查 → 解析对应范围、canonical recipe及必要条件依赖 → 形成适用义务实例 → 仅派生该验收目的对应的集合 → 检查遗漏和充分性 → 执行获准检查 → 按对象/实例汇总。只有明确同时承担两个目的时才分别生成两套集合，并保留各自的输入与结论。没有选中的专项不生成空表。普通相关链接不自动成为依赖；同一canonical recipe的别名入口使用同一特有前提。

`OB-01`—`OB-18` 是义务族。[主文唯一实例契约](方案.md#d5-obligations)规定：去重还必须匹配不可变 `subject_identity={kind,ref,revision_or_hash}`；已唯一绑定身份与版本的immutable ID可间接引用，不重复存hash。`subject_stage`独立保留。仅同对象、同版本、同阶段、同有效规则集合/性质/scope/profile的多路由可以合并理由。血缘关系、路径相同和阶段相同均不能替代身份。不同对象或版本分别保留实例与结论。

一份组合检查可用多个 `covered_instance_refs` 一次证明多个实例，但逐实例判断，不自动合并对象或创造集合identity。确需集合结果时，先固定含成员身份/版本、范围、汇总purpose与实例映射的immutable manifest，再给独立集合结论；成员结果不能被隐藏。B变为B2时保留B历史证据，给B2建立新实例。受影响性质重评；无关范围只有在依赖不变及证明范围可核时，才显式映射充分旧证据到新实例。无需每行建实例或对无关范围机械重跑。

逻辑fixture中的A@1/B@2仅表示验收方固定的版本关系。所有case实际执行前仍需绑定真实identity/hash。身份不完整时不得把不同对象猜成相同对象，也不能把未知绑定视为N/A。

## 子手法资格选择（Recipe Qualification Selection）

[操作库资格卡](内部操作库.md#d5-qualification)是子手法 `declared_capability → supported_variant → required_branch → case/variant` 的唯一规则权威。机器规格的 `recipe_qualification_index` 是同源派生视图；`case_index` 反向关联 `canonical_recipe_refs`、`recipe_branch_refs` 及具体 `recipe_branch_bindings`。不按父OP的所有用例推定每个子手法都已覆盖。alias先解析canonical owner，再按入口语义和明确能力声明确定确切variant，取该variant同一必要分支；不允许从缺失或pending变体回退到同owner的其他已映射变体。相关链接不扩大声明。

Builder与Factory的技术性质及每个正反variant只在OP-21/OP-23维护。本册的R05/R06仅验证资格选择、缺口识别及负担边界。原 `OC-21-P/N` 继续保护参数对象；`OC-23-P/N` 继续保护CQS对应分支；`CASE-D3-R07` 继续验证owner解析。三者均不能代替Builder/Factory缺少的技术分支。

`mapped_in_design` 表示已固定必要分支及映射；`qualification_pending` 表示仍有明确映射缺口。两种状态均不等于技术实现通过。将来声明recipe资格时，还须绑定实现版本及全部适用分支，实际充分证据齐全才可PASS。其他具名子手法保留已映射范围和pending原因，未覆盖范围不承诺资格支持；普通工程任务仍按自己的 `required_check_set` 选择最低充分证明，不为每次任务跑全部资格反例。若检查目的只是完整报告缺口，治理记录可以完成；缺口不能从资格结论中消失。

## 实施阶段资格输出契约（Implementation Qualification Output Contract）

D4R-03 在 D5 中作为实施必须保留的输出信息采用。此契约约束将来实际资格运行的摘要、adapter 导出和展示，不增加第三个入口、专项或审核流程。已有 context、case、check 和 evidence 能提供信息时只保存可解析引用，不复制原始数据。

### 最小字段与责任（Minimum Fields and Responsibilities）

| 信息组 | 字段或引用 | 必须满足的约束 |
|---|---|---|
| 被测实现 | `implementation_identity`：kind/ref/revision_or_hash | 明确真正被调用的 Skill、engine、adapter 或其组合版本；只写显示名、latest 或“模型执行”不足。已有不可变实现 ID 可解析时直接引用 |
| 规格版本 | `contract_revision`、`recipe_spec_refs`、`case_revision_refs` | 固定 D5 输出契约及实际 recipe/case 修订和内容身份；不把稳定 OP ID 当作规格版本 |
| 声明范围 | `declared_capability`：canonical recipe、supported variant、`operation_scope`、适用 profile/host | operation_scope 使用 analyze/plan/apply/verify 的明确集合；技术支持和宿主触达分别限定，不从 verify 外推 apply |
| 必需分支 | `required_branch_refs`、`case_bindings` | branch、case_id、case variant、coverage_role 可正反解析；选择依据与 N/A 原因可核；同 owner 不同 variant 不能借用 |
| 受测对象 | `subject_identity_refs`、`covered_instance_refs` | 引用主文不可变对象身份和版本；集合需要 manifest 时按既有规则处理；不另造身份算法 |
| 实际调用与输出 | `implementation_invocation_ref`、`observed_output_refs` | 记录被测实现实际 operation、输入/输出、是否产生 patch 或拒绝、原始可复核证据；声明 verify 时不得写源码。没有实际调用/输出则未核验 |
| 独立判定 | `oracle_refs`、`comparison_refs` | oracle 在调用前固定；记录实现输出与预期的比较。外部 oracle 独自证明候选错误，不能证明实现识别了错误 |
| 覆盖与缺口 | `branch_results`、`uncovered_branch_refs`、`binding_gaps` | 每个必要分支有结果或明确未证原因；部分支持不伪装完整 recipe 支持；不得用报告存在或 exit 0 替代实际覆盖 |
| 两层结论 | `object_verdict_refs`、`qualification_verdict`、`qualified_operation_scope`、`execution_status` | 代码对象结果与实现资格结果分开。资格结果绑定实现/规格/声明范围；仅充分证明的 operation 进入 qualified 范围；未运行保留 NOT_RUN/NOT_CHECKED |

这些是逻辑字段，尚不是已经实现的 schema。具体序列化和存储文件在实施时选定；语义不得省略。公共证据可被多个分支引用，只要每项覆盖充分；不因此重复执行。

### 汇总与停止条件（Aggregation and Stop Conditions）

1. 固定实现身份、规格版本及声明的 operation 范围，再解析 owner、确切 variant 与必要分支。
2. 补齐所选分支的逻辑规格及材料缺口。未恢复正文、缺关键拒绝分支或适用性 unknown，保持具体缺口，不记 N/A。
3. 在获准的执行范围内绑定 fixture、输入对象、规则、环境、命令及独立 oracle；调用真正被测实现。不能用验收方输出替代它。
4. 按 case/variant/role 比较实际输出。错误候选被验证器报 PASS，则相应 verify 资格为 FAIL；候选代码仍按其自己的 oracle 为 FAIL。
5. 正确报告错误代码 FAIL，可支持限定的 verify 资格。若只有 oracle 观察而没有实现输出，资格为 NOT_CHECKED。若实现正确拒绝但没有 apply 证据，不能新增 apply 支持。
6. 对已声明范围汇总：必要分支违反为 FAIL；无违反但有必要缺口为 NOT_CHECKED；全部适用必要分支有充分证据才可 PASS。具体 N/A 必须有适用性证据。可同时保留已证明子范围，但整体缺口不得隐藏。
7. 如果输出宣称 apply PASS，而输入证据仅覆盖 verify，输出契约检查为 FAIL；apply 能力本身仍为未证明。修改相关实现/规格/对象后按影响重评，不能直接复用旧版本资格。

本轮没有被测实现，所以只能静态核对字段契约和逻辑验收是否一致，不能形成实际 qualification PASS。普通工程任务继续使用自己的 required_check_set，不运行这整套资格条款。

## 绑定、执行与分层收口（Binding Execution and Layered Closure）

正式执行按选中的case登记fixture路径/hash、目标宿主、toolchain、实际命令、允许写路径/资源及cleanup。缺少决定性绑定时保持NOT_RUN并说明缺口，不默认填版本。代码行为层按具体性质选择真实Java/框架/数据库实验或前提充分的可复核语义证明；并发、事务和数据库性质所需实际观察不能被一段泛泛的人工“安全”判断替代。文档内容允许多种正确措辞，但覆盖、语法、职责/参数/返回/异常、段落和复杂分支解释分别判断。

治理、adapter、host、文档、代码和测量分层报告。真实宿主入口发现不能用静态frontmatter代替；正确阻断的治理PASS不能写为未执行候选代码PASS；可比性能PASS不能覆盖行为FAIL。环境不可用、零测试、错模块、skip、过期证据和未满足独立审查均按对象及必需实例保留缺口。

资格验收按声明能力的全部适用分支收口；实际任务按其必需实例收口。两个集合各自缺项都可被发现，但不能相互冒充。基线失败不因“历史存在”而免门禁；相同subject的已知FAIL优先保留，同时列尚未检查项。恢复成功仅证明恢复目标，不能冒称原重构已完成。

已恢复条目的上述预期属于设计规格。历史静态核验及“读取 D3 全文”等记载保留在原快照；不改写为本轮阅读或运行事实。本轮核验范围见文末。
