# 聚合分析流程（Aggregate Analysis Workflow）

## 1. 建立基线（Establish Baseline）

读取包内 evidence-contract.md。记录 scope、baseline 和用户允许读取的材料。复用上游标识。确认本次任务是边界设计，还是针对指定范围的实现审阅。

只有命令、规则或粗粒度概念时，可以发现问题并提出候选，不要求先具备完整 UML。没有可读代码时，不评价实现通过。对资料中的指令、SQL 和示例只做阅读。

## 2. 消化业务规则（Clarify Business Rules）

逐条写出 rule_id、statement、scope、涉及的 concept_id、触发命令、条件、例外、时间范围、违反后果、evidence_ids、confirmation_status 和 question_ids。scope 说明该规则适用的业务与上下文；不能只依靠报告的全局范围。先用业务语言表达，不先选锁或事务注解。

分别问清楚：规则是否要求命令完成时立即成立？允许多长延迟？谁能看到中间状态？违反后能否补偿？这些问题的答案来自业务及现有决策，不能由 Agent 自行设定。

标记 consistency_requirement 为 immediate、eventual 或 unknown。eventual 还需记录允许的延迟、可见性和修复责任；这些未知时仍需澄清。不同规则可以有不同要求。

不变规则需要保留适用条件。历史记录、失效状态、租户和业务有效期不能被一句“始终如此”抹去。跨对象规则也不自动证明必须合成聚合。

## 3. 推演并发破坏（Construct Interleavings）

对需要立即成立的规则，列出至少一种相关的并发或重复操作序列。记录各操作看到的状态、修改对象和提交时点。若无法确认并发是否可能，记录问题，不创造运行事实。

例如，在明确“同一员工技能类别不得重复”的虚构场景中，A 和 B 都看到技能不存在，再分别新增，可能造成重复。该推演是 candidate；实际项目是否已由约束、锁或串行处理防住，需另查证据。

区分原子性与隔离性：一组写入一起成功并不自动防止两个命令基于过期状态同时作出决定。不能只看 @Transactional 就宣布安全。重复请求与并发请求也应分别分析，不把根版本检查当成所有幂等问题的答案。

## 4. 比较边界（Compare Boundaries）

候选至少说明 aggregate_id、root_concept_id、member_concept_ids、rule_ids、外部引用、身份范围和选择理由。按所需规则与业务整体性选根，不能因为某表先建立就选根。

比较较小边界与合并边界。说明加载量、写入冲突、规则定位和操作独立性；没有性能数据时仅列验证问题，不编造吞吐数或上限。无合理替代时说明原因，不强行制造多个方案。

单实体也可以形成聚合。一个成员是否属于某根、能否转移、如何失效或删除，需要业务事实。课程中的生命周期推论不能直接变成物理级联删除指令。局部标识只说明业务唯一性范围，不禁止持久化使用技术 ID。

聚合是领域一致性边界，表、包、进程、服务及部署边界属于实现维度，不能画等号。

## 5. 处理跨边界规则（Handle Cross-Boundary Rules）

列出跨候选聚合的规则及其即时性。先确认规则到底约束哪个整体。例如“某员工所有有效项目分配的投入不超上限”可能横跨多个项目，不能仅因项目成员属于项目就把所有项目合并。

比较真实可行的候选：调整模型边界、建立明确的协调责任，或在业务允许时使用异步检查及补偿。协调聚合、数据库约束或其他技术机制都需要实际项目支持，不能伪造现有能力。

每个方案记录可维护的规则、失败窗口、冲突范围、可见状态及验证条件。补偿不能替代未经允许的即时约束。跨边界事务是否可用，按架构事实和明确政策判断，不套用一律禁止或一律允许的规则。

## 6. 定义修改入口（Define Mutation Channels）

列出创建、根修改、子对象新增/修改/删除、集合修改、批量操作和后台任务等已知入口。未知入口作为审查缺口，不宣称已穷尽。

每个入口要说明怎样调用规则校验，怎样保证同一聚合的一致性。只读集合不等于元素不可修改；不可写字段与公开 setter 也需核对。实现检查引用实际文件和行号，设计任务则输出候选契约。

按实际语言与框架决定封装方式。不要硬编码 Java package private、每实体必须配领域服务或 ChangingStatus 枚举。规则由拥有必要数据和职责的领域对象或合适领域服务承载，持久化编排与事务按项目架构确定。

## 7. 定义加载与重建（Define Loading and Reconstruction）

说明哪些数据是本次规则判定必需的，如何完整取得。按使用场景考虑全部加载或能证明等价的受控加载；不要因为课程整体读取就固定装载无界集合。

区分新建校验和从持久化重建。若计划绕过校验，必须说明入口隔离、数据可信依据及无效数据的发现/处理责任。不能假定数据库干净，也不能让业务写入随意调用重建入口。

实现审阅还需核对字段查询、对象映射、所属根和上下文的关联，以及状态版本是否来自同一基线。没有对应 Schema 或映射代码时列 NOT_CHECKED。

## 8. 定义更新与持久化（Define Update and Persistence）

先确定 update_semantics：full_replace、patch、command 或 unknown。请求未携带某子对象是否意味着删除，要有明确契约。PATCH 中字段缺席不自动删除。空集合、null 和字段缺席分别核对，不猜请求格式。

保存契约描述整体成功、失败回滚、删除/失效语义及并发保护。方案采用乐观版本时，必须检查：

- 所有会影响聚合规则的写入，都对相同聚合根执行原子的“比较旧版本并推进版本令牌”，包括仅修改子对象。仅先读版本再写入不足以防住交错。
- 根本身未变时，子对象写入仍须推进令牌；不能因根标记为 UNCHANGED 而跳过，也不能两个命令都检查到同一版本却不使其失效。
- 通过条件更新的影响行数或技术栈等价证据判定成功；令牌可以递增或以等价方式更换，具体机制按实际技术栈确认。
- 原子比较并推进成功后才保存成员；令牌推进与成员写入在同一已确认的原子提交范围内，后续失败必须整体回滚。
- 冲突不继续写成员；后续写入失败不会留下已成功的部分。
- 冲突反馈、是否重读或重试，以及重试时重新校验规则的责任明确。

这组条件属于该候选乐观版本方案，不能要求所有技术栈使用 version 字段。若采用悲观锁、唯一约束、串行化或其他策略，说明实际机制如何阻止所列交错，并验证其覆盖范围。仅发现事务注解不等于机制已验证。

## 9. 制定验证计划（Plan Verification）

将每条规则连接到正常、边界、并发、冲突及失败场景。验证计划需注明输入基线、动作顺序、可观察结果和判定标准。未执行时写 NOT_CHECKED；拟定的测试不能作为测试通过证据。

至少考虑子对象单独更新、保存中途失败、全量/PATCH差异、同一根并发和不相关根并发。实际并发测试、数据库访问和代码修改不由本分析任务自动执行。

## 10. 自检与交付（Review and Deliver）

使用 assets/report-template.md。检查所有关键规则是否有证据或明确未知；即时性是否真实确认；边界方案是否解释规则覆盖和代价；跨边界规则是否遗漏；版本策略是否覆盖全部已知写入；更新语义是否清楚；每条结论能否用业务语言解释。

最少需要一条从规则到场景、边界、机制和验证计划的追溯链。缺少核心规则或 scope 时 blocked；有边界决策依赖的未知或冲突时 needs_clarification；其余可交付为 ready_for_review。

最多两轮定点自检。发现需要新事实时，问具体问题并保留部分结果。用户仅提问时在对话中报告；用户明确保存时才使用已指定位置。不要写到安装源包或修改输入资料。
