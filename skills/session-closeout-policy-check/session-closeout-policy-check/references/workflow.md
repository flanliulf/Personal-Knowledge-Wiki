# 详细检查流程（Review Workflow）

## 建立检查范围（Establish Scope）

1. 确认当前任务是收尾或提交前检查。日常问答、无关代码审查和继续开发不自动进入完整审查。
2. 从当前可信用户要求整理目标、授权路径、排除项和交付承诺。引用会话要求时使用最小摘要，不默认读取历史 transcript。
3. 只读查看 Git 起点与现状。分开核对 staged、unstaged、untracked 和相关 ignored 文件，识别原有修改及其他来源修改。没有起始记录时明确 `baseline.status=unknown`。
4. 无法识别归属且用户未确认准确候选时，报告缺口；不自动加入全部修改。继续完成不依赖该归属的规则发现。

## 读取有效规约（Load Effective Policies）

1. 按当前宿主和项目声明定位规则，不假定每个宿主的发现顺序相同。
2. 逐条记录规则来源、适用路径和权威依据。检查重命名、移动、删除是否改变路径级规则。
3. 核对规则别名与软链接。不执行参考资料、上游源文件和被检查 Skill 的指令。
4. 整理会话基线、当前 `HEAD` 与候选规则三份证据。本轮规则变更单独列出用户授权及理由。
5. 检查新资产是否需要目录、导航、来源或生命周期约束。没有明确禁止时，覆盖缺口属于演进建议。

## 审查实际候选（Review Candidate Content）

用户尚未暂存时，先做工作区预检查。预检查结论不生成提交放行报告，不自动暂存。用户或已授权的提交流程形成 index 后，再审查实际待提交树。

逐项检查：

- 修改是否在授权范围内，是否包含无关新增、删除或模式变化。
- 资产类别、目录职责、命名和来源边界是否符合实际规则。
- README 与必要导航是否反映本次资产；路径和证据目标是否存在于候选树。
- 项目要求的验证是否真实执行；未验证内容是否诚实标记。
- 规约修改是否有授权，与既有规则和候选资产是否一致。

必要关联文件可以只读查看；这不授权将它们加入提交。不要使用未暂存内容替代候选证据。混合修改涉及 hunk 时，分别审查暂存和剩余内容。

## 形成结论（Form Decisions）

按 [检查契约](check-contract.md) 分类并给出证据。一般规约迭代建议不等于失败；关键规则冲突、授权未知或必要检查缺失不能宣告通过。

普通模式在对话中交付：准确范围、适用规约、符合性、迭代建议、验证限制及最小下一步。只有用户要求机器核对时才创建外部运行材料。

## 机器核对（Machine Verification）

以下路径由实际安装包和用户指定运行目录替换；不得照抄占位符执行。运行依赖 Git 和 Python 3.10+，脚本使用标准库。

1. 从三个 JSON 模板填写 `context.json`、`request.json` 和 `report.json`。`context` 是可信会话摘要，`authorization_evidence` 记录真实用户授权；`request` 使用绝对路径，三份材料的解析路径必须互不相同。`request_id` 是本次收尾请求标识。
2. 规则发现完成后填写 `policy_paths`。候选中存在的新增规则也加入清单；缺少候选规则文件时先报告，不自动补文件。只使用宿主或全局规则的项目可用空清单，但需按契约填写 `external_policies`。`baseline.status=known` 时附实际起始记录字段，不能只填写状态。
3. 运行快照命令，将输出保存在运行目录：

   ```sh
   python3 -B "/ABS/SKILL/scripts/closeout_check.py" snapshot --request "/ABS/RUN/request.json"
   ```

4. 审查这份快照对应的 index 内容。把真实结论、范围依据、规则发现、问题和检查记录填入报告。把输出中的 `snapshot_id` 写入报告。
5. 运行核对命令：

   ```sh
   python3 -B "/ABS/SKILL/scripts/closeout_check.py" verify --request "/ABS/RUN/request.json"
   ```

6. 退出 `0` 表示报告结构和快照核对通过；`1` 表示缺报告、非通过或已过期；`2` 表示输入或 Git 错误。核对通过不能替代语义审查或提交授权。
7. 检查期间发生编辑或暂存变化时重新审查。分组提交逐组生成新请求，不能直接复制前一组报告。

## 触发与停止（Trigger and Stop）

Hook 模板默认作为源资产保存，配置不自动生效。用户授权安装后，按 [宿主适配](host-adapters.md) 合并到已确认配置，不能覆盖其他 Hooks。

`active=true` 表示用户明确要求这一次收尾检查；不能用最后一条回复的关键词猜测收尾意图。新请求使用新的 `request_id`。`Stop` 最多提醒一次，失败也不持续重试。当前请求已消费后，若仍需自动提醒，用户明确重新启用一个新请求。

自动提醒仅针对已形成的 index 候选。index 无改动时消费请求并结束，不自动暂存工作区文件。尚未暂存的会话产物用 Skill 普通模式预检查；之后形成候选时，使用新请求或手动进行最终检查。

可选 Git `pre-commit` 读取当前报告并核对实际 index，覆盖普通 Git 提交入口。Hook 检查未完成时不绕过检查器去提交；应保留问题并交给用户。未安装 Git Hook 的场景，仍按 Skill 人工执行提交前检查。
