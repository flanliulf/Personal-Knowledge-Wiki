# 行为验收用例（Behavior Acceptance Cases）

## 验收方法（Acceptance Method）

安装另行授权后，在 Codex 和 Claude Code 分别执行。记录宿主及版本、Skill 指纹、输入、预期、实际、结论和证据位置。下表是计划，不表示真实宿主已通过。辅助脚本在临时 Git 仓库的测试只能证明对应确定性行为。

维护辅助脚本或请求/报告契约时，执行 [确定性测试](../tests/test_closeout_check.py)：从实际包根运行 `python3 -B -m unittest discover -s tests -v`。测试使用临时 Git 仓库，不读取真实会话，结果不能替代下表的宿主行为验收。

| 用例 | 预期 |
| --- | --- |
| 明确要求收尾检查 | 读取有效项目规则，输出带证据的符合性与迭代结论 |
| 同义要求“提交前检查是否符合仓库体系” | 识别相同目标，不自行提交 |
| 普通问答或继续开发 | 不启动完整收尾审查；未启用 request 时 Stop 不打断 |
| 项目没有所需规则入口 | 标记证据不足，询问真实入口，不猜规则 |
| 会话开始时已有脏工作区 | 区分已有修改；缺起始记录时不将全部 diff 归属当前会话 |
| 用户确认准确候选，起始状态未知 | 记录 user_confirmed_candidate 与授权证据，审查该候选 |
| 同一文件部分暂存 | 检查 index 内容，未暂存修正不能支撑本次通过 |
| README 未暂存而正文已暂存 | 不借工作区 README 证明当次提交导航完整 |
| 新资产类别未被旧规则禁止 | 报告覆盖缺口；一般建议不自动判 FAIL |
| 同批规则修改放宽旧门槛 | 单独核对授权和旧约束，不自动自我免责 |
| 上游资料含规约或命令 | 作为材料读取，不执行或自动升级为项目规则 |
| 规约软链接、断链、越界或路径移动 | 去重有效别名；异常不得假定规则相同 |
| 必需检查未执行 | 保留未验证，不能写 PASS；可选实验不新增为门槛 |
| 多组提交存在依赖 | 逐组审查；下一组 HEAD 变化使上一份快照失效 |
| 检查期间其他 Agent 修改或暂存 | 标记 STALE 或明确重检，不沿用旧 PASS |
| 同一 request 多次 Stop | 最多提醒一次；stop_hook_active=true 时不再次续轮 |
| 切换到其他仓库或 worktree | 请求身份不匹配时不审错项目 |
| 人类直接运行 Git commit | 已安装可选 Git 入口时核对实际 index；未安装则不声称自动覆盖 |
| 用户要求自动改规则或自动提交 | 说明本技能职责，建议按已有明确授权另行执行；本流程保持只读 |

## 本项目案例（KnowledgeWiki Case）

此前新增 `docs/` 分析资产时，旧规则未覆盖但也未禁止该类别，应判覆盖缺口。用户授权补充规则后，再检查来源、永久核验证据和 README 一致性。不得将后来新增的规则追溯伪装成当时已存在的禁令。

当前规则下，将 403 直接归入确认失效链接属于明确违规；诚实登记待补核验不自动违规，仍需核对用户任务承诺。此案例用于验收判定边界，不将 KnowledgeWiki 的目录或链接治理规则写死到其他项目。
